## SuperSplat #1053：这次是非常实在的大 PLY 加载优化

Merge commit：

`7aec7f79c7114e01553694b80aeb2b86022216fe`

PR：

**#1053 — Load PLY in a single sweep, show load progress, and fix the WebP decoder mismatch**

[SuperSplat PR #1053](https://github.com/playcanvas/supersplat/pull/1053)

此前从 SuperSplat 3.0 开始，大 PLY 加载近似是：

```text
PLY
 ↓
第一遍读取 positions
 ↓
计算 Morton order
 ↓
第二遍按 Morton permutation 读取全部属性
 ↓
GPU upload
```

问题在于第二遍的 `PermutedChunkSource` 最终容易退化成大量随机 gather。

#1053 改成：

```text
PLY
 ↓
按文件原顺序只 sweep 一遍
 ↓
直接填 texture arrays
+
计算 AABB
 ↓
直接在 transformA 的 xyz float view 上做 Morton sort
 ↓
原地 permutation
 ↓
GPU upload
```

而不是先构造单独 `x/y/z` 表再随机读取源文件。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

## #324：1 亿级 Adaptive Decimation

以前 adaptive planner 会维护不少 scratch 文件，并做 KD-order staging。

现在：

- block plan 留 RAM；
- 默认**不再偷偷往 output directory 写 scratch**；
- 只有真正超过 memory budget 的深层 decimation 才要求显式 `--scratch-dir`；
- planner heap refresh / invalidation 改造成更 cache-friendly 的路径；
- PLY gather typed-array view 不再 per-record 重建。

维护者测得：

| 场景 | 旧 adaptive | 新 adaptive |
|---|---:|---:|
| Poland **106M**, DC-only, 50% | 10m34s / 4.7 GB | **7m53s / 4.5 GB** |
| Parish **35M**, SH3, 50% | 5m16s / 4.7 GB | **4m08s / 4.7 GB** |

## #325：PLY → SOG 性能回归终于基本追回来了

核心变化有三项：

```text
过去：
position / geometric / color
各自读 source

现在：
一个 chunk 一次 source.read()
同时 gather 三层
```

同时：

```text
scale/color quantize
SH k-means
Morton sort
WebP encode
```

重新并行，而不是 3.x streaming rewrite 后串行等待。

最重要的是 Morton：

```text
TypedArray.sort + JS comparator
         ↓
stable 3-pass LSD radix sort
30-bit Morton code
```

# 4. PlayCanvas Editor 2.32：Streamed SOG 的预算控制终于更像产品能力

PlayCanvas 官方 9 月 22 日发布了 Editor 2.32 技术说明。

GS 方面最重要的是组件级 LOD 控制从过去的：

```text
LOD Base Distance
LOD Multiplier
```

改成：

```text
LOD Range Min
LOD Range Max
LOD Falloff
```

。[PlayCanvas 博客](https://blog.playcanvas.com/new-in-playcanvas-editor-joints-parallax-occlusion-and-splat-lod/)

`Range Min/Max` 控制该组件允许使用哪些 LOD levels，而 `Falloff` 决定它在全局 splat budget 内，细节多强地集中在近处。

例如：

```text
城市环境
→ 允许 LOD 0–6

Hero 建筑
→ 限制到较高质量 LOD

背景扫描
→ Falloff 更激进
```

这样多个高斯资产争用同一个：

> **Global Splat Budget**

时，设计师终于能明确决定谁优先。

非常关键的一条限制：

> **LOD Range 只对 Streamed SOG octree 有实际意义。**

普通：

- `.ply`
- 单 `.sog`

只有一个 LOD，因此这些字段虽然会显示，但没有 level 可选择。[PlayCanvas 博客](https://blog.playcanvas.com/new-in-playcanvas-editor-joints-parallax-occlusion-and-splat-lod/)

## #2287：切换训练项目会因为旧 CUDA stream 崩

Commit：

`ac33385a12fd0667a97e6ca4855b14ebf35c3284`

此前一个用于 Q16 SH mutation 的 workspace 生命周期是：

```text
整个 App 生命周期
```

但它的 GPU buffer 却绑定到：

```text
创建它的 training CUDA stream
```

于是：

```text
Project A 训练
↓
workspace 绑定 Stream A
↓
切换项目
↓
Stream A 被销毁

Project B 训练
↓
workspace 扩容 / free
↓
在已经死亡的 Stream A 上释放
↓
context is destroyed / silent crash
```

。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

现在改用 LichtFeld 自己的：

```text
Tensor memory pool
+
record_stream()
```

让 workspace 正确跟随当前 stream。

回归测试甚至显式：

1. 建 Stream A；
2. 用 workspace；
3. release + destroy A；
4. 建 Stream B；
5. 继续扩 workspace；
6. 检查没有 stale-stream free。

[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

对长期：

```text
训练 A
→ 看结果
→ 切 B
→ 再训练
```

的 Studio 使用，这是非常实际的 P1 稳定性修复。

这会直接回答一个 Metaflow 很重要的问题：

> **以后多场景拼装时，能否只靠 Engine/Editor 原生 budget scheduler，而不再自己写大量 LOD policy。**

## ③ Spirula 顺序 SfM：拿真实视频抽帧做 A/B

普通 global mapper

保持：

完全相同。

记录：

尤其找：

如果 sequence-aware mapper 在这些场景里明显稳定，它会比单纯“抽更多帧”更值得进入视频 3DGS preprocessing。

## 今日结论

今天没有新的范式级 P0，但 **PlayCanvas 工具链出现了一次非常明显的“性能收敛”**。

SuperSplat #1053 和 SplatTransform 3.6.x 实际上在解决同一个问题：

> **当 Gaussian 上到千万乃至上亿以后，瓶颈已经不只是 GPU rasterizer，而是文件怎么读、怎么排 Morton、数据要扫几遍、线程如何重叠、以及大模型降采样如何在有限内存内规划。**

22.9M PLY：

> **加载约从 8 秒级进入 5 秒级。**

17.5M Morton：

> **2.387 s → 0.537 s。**

106M adaptive decimation：

> **10m34s → 7m53s。**

这已经不是“微优化”。

另一方面，PlayCanvas Editor 的 LOD Range/Falloff、Engine 对宿主 GPUDevice 的初步支持，以及 SuperSplat Viewer 1.32 的可嵌入 API 放在一起看，也越来越接近你们需要的架构：

```text
宿主 App / Metaflow
        ↓
独立业务 UI / Agent / Map
        ↓
可嵌入 Viewer
        ↓
统一 PlayCanvas GS runtime
        ↓
Streamed SOG + Budget / LOD
```

而训练侧的新信号也很明确：

**LichtFeld 正在补 Studio 级稳定性，Spirula 正在利用“视频本来就是有顺序的”这个信息增强 SfM，SLAM 研究则越来越重视 uncertainty 与特殊运动坐标系，而不是继续单纯追 PSNR。**
