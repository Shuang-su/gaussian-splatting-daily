# 3. 可实际运行的开源项目

## P1：Gaussian-Splat-Lite v1.1.6 / v1.1.7

这是今天 Web Renderer 方向最实质的正式版本变化。

仓库本身是 Three.js 生态里的原生 GS renderer，支持 WebGPU / WebGL2、PLY/SPZ/SOG/RAD、streaming LOD、depth rendering 和 GIS/ECEF precision，许可证 **Apache-2.0**。[GitHub](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite)

### v1.1.6：stochastic 不再等于“完全不考虑深度顺序”

版本提交：

`f397c56259096438674dc7398d3d599badad7a24`

核心新增：

```text
WebGPU
stochastic / Auto camera moving
        ↓
16-bit front-to-back depth key
        ↓
4-pass GPU radix sort
        ↓
stochastic render
```

参数：

```text
stochasticSort = true
```

默认开启。

[Gaussian-Splat-Lite v1.1.6 commit](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/f397c56259096438674dc7398d3d599badad7a24)

这里很有意思，因为它和 SuperSplat Viewer #314 采取了不同折中。

SuperSplat #314 更接近：

> **彻底摆脱完整排序，用 depth buckets + stochastic survival + TAA。**

Gaussian-Splat-Lite 则认为：

> 即使 stochastic，不做精确 back-to-front alpha sort，也值得做一个**廉价的 16-bit front-to-back order**，因为这样能更早写 depth，减少后面 fragment overdraw。

所以：

```text
Sorted alpha path
→ 精确 back-to-front

GSLite stochastic
→ 粗/廉价 front-to-back

SuperSplat stochastic
→ projection / bucket / stochastic depth + temporal resolve
```

三者已经形成不同的性能设计空间。

---

## WebGL 也不是直接放弃排序

WebGL / fallback 路线无法像 WebGPU 那样直接 GPU radix：

```text
Camera motion
↓
Worker / WASM
异步 16-bit front-to-back sort
↓
新排序尚未完成时
继续使用上一份 matching data + indices
```

而 `Auto` 模式 Camera 停止后：

> 恢复普通 back-to-front sorted rendering。

所以它是在明确优化：

> **运动时 latency / overdraw**

而不是永久牺牲静止画质。

## Radix 本身也专门优化了一轮

Commit：

`b2dcfe65cf783d7cc73541a2ac58a3e54bac3784`

主要改动包括：

- prefix scan 的固定 level 在 shader build 时直接展开；
- 减少 runtime loop；
- shared digit mask 内存布局重排；
- prefix 只读取一次进入 local offsets；
- mask count 和 clear 合并到 atomic operation；
- 减少 shared mask / prefix buffer access。

排序结果和 GPU buffer 尺寸保持不变。

[WebGPU radix optimization](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/b2dcfe65cf783d7cc73541a2ac58a3e54bac3784)

**上游没有给出本次优化后的 GPU ms benchmark。**

所以今天不能写成：

> “radix 快了 X 倍”。

这条只能定性为优化已落地。

## v1.1.7：修掉 TAA 噪声“朝固定方向漂移”

随后约一小时又发布：

`7caa9b1bbc393a27412f0118ed125362d61a1262`

修复：

> stochastic noise 在 TAA 下出现 constant directional drift。

根因是 temporal blue-noise offset 的使用顺序，现在重新排列 across all rendering backends。

[Gaussian-Splat-Lite v1.1.7 commit](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/7caa9b1bbc393a27412f0118ed125362d61a1262)

```text
→ 看起来只是正常 grain

→ 人眼非常容易察觉
```

**评级：P1 / A。**

# 5. Viewer / Editor / Web / Mobile / XR

今天真正新的 Viewer 变化是前述 **Gaussian-Splat-Lite 1.1.6/1.1.7**。

它和 SuperSplat #314 放在一起看，非常值得长期追踪。

现在 Web stochastic GS 实际出现两种路线：

| 方案 | 运动时排序 | 降噪 |
|---|---|---|
| SuperSplat Viewer #314 | 不做完整传统 sort；depth buckets / stochastic raster | 自带 TAA + reprojection |
| Gaussian-Splat-Lite 1.1.7 | 16-bit front-to-back cheap sort | StochasticTAAPass |
| 普通传统路径 | full back-to-front | 不需要 stochastic temporal resolve |

这里面真正值得以后 benchmark 的不是单纯：

> 哪个 FPS 高。

而是：

\[
\text{GPU Time} \times \text{Temporal Error} \times \text{VRAM}
\]

三者的 Pareto frontier。

## 为什么它不是“把空间切成 4 个 box 就训练”

很多大型 GS 分块思路最简单是：

```text
XYZ bounding box
↓
grid / quadtree
↓
各训各的
```

问题是 Camera 不按几何 box 拍摄。

一个房间边界附近可能：

- 两边 Camera 都能看见；
- 同一面墙跨 tile；
- far background 被多个 tile 重建；
- 边界处极容易出现 seam / floater / exposure drift。

Spirula 新实现首先构造：

> **Camera Covisibility Graph。**

---

# 14. Covisibility 来源按数据质量分三级

### COLMAP

优先使用：

```text
真实 feature tracks
```

两个 Camera 共同观察多少 3D point，就形成多强的 graph edge。

### Nerfstudio / Metashape

如果没有完整 track：

```text
Seed Point Cloud
↓
投影到各个 Camera
↓
估计共同 visibility
```

作为 proxy。

### 只有 Pose

再退化为：

```text
k nearest camera centers
×
(1 + cos(view-angle))
```

所以它至少尽量按：

> **Camera 共同看了什么**

而不是：

> **Camera 在哪里。**

---

# 15. 真正分区使用 normalized cut

不是 k-means。

它使用：

> normalized graph Laplacian 的 Fiedler vector

递归二分。

而且加入几个生产约束：

- 每边至少保留 parent 的约 30%；
- 防止 normalized cut 不停削一个小弱连接 cluster；
- disconnected component 单独处理；
- boundary refinement 会让 Camera 移向共享更多邻接的 part；
- 可以指定固定 `--parts`；
- 或 `--max-images` 自动切到每块不超过一定 Camera 数。

这对：

```text
长走廊
楼层
街区
360 scan
复杂环形 Camera path
```

比简单 Euclidean clustering 合理很多。

---

# 16. 最值得看的其实是 Ring Camera

每个 part 不是只用自己 core Camera。

如果一个外部 Camera 看到：

> 至少一定比例属于这个 part 的 point，

它会成为：

```text
ring camera
```

也参与这个 part 的训练。

目的：

```text
Part A     seam      Part B
  ↑                    ↑
camera A            camera B

+ 两边借对方的一部分 Camera
```

让两个模型在边界看到：

> **相同 supervision。**

文档甚至直接说：

> Ring 是当前设计里对 seam 最重要的一项变化。

---

# 17. 空间所有权不是普通最近邻

训练完之后还必须回答：

> 边界附近这个 Gaussian 最终属于 Part A 还是 B？

它构建 `LabelField`。

Seed 包括：

- sparse point；
- cameras。

但距离不是单纯：

\[
||x-p||
\]

还会看：

> Seed 当初是从哪个方向被观察的。

如果 query point 在 seed 的**背面**：

距离被乘以较高 penalty。

如果 Gaussian normal 朝向和观察方向明显冲突：

再加入 orientation penalty。

直觉上：

```text
同一面墙

房间 A 看到正面
房间 B 看到背面

普通 Euclidean nearest
→ 容易互相抢

visibility-aware metric
→ 正面归 A
→ 背面归 B
```

这对室内建筑分块非常合理。

# 18. Merge 是 Hard Ownership，目前不做 Feather

每个 part 训练完成后：

```text
part training frame
↓
world_from_train
↓
恢复原 dataset coordinates
↓
判断每个 Gaussian 的 spatial owner
↓
只保留 owner part 的 Gaussian
↓
统一 SH degree
↓
concatenate
```

当前明确：

> **Hard ownership。**

没有：

- opacity feather；
- seam band joint optimization；
- cross-part blend。

作者把这些留到之后根据真实 seam 再判断是否需要。

# 今日结论

今天最值得记住的是 **LichtFeld Trainer 的状态发生了质变**。

昨天还可以描述成：

> “正在把 CUDA kernel 调用抽象成 backend table。”

今天已经变成：

```text
Trainer shared code
✓ backend-neutral

No-CUDA build
✓

Vulkan work queues
✓

Fence / timing
✓

Readback / upload
✓

Image pipeline
✓

Splat storage
✓

Training kernel
✗
```

这意味着以后真正要等的已经不是：

> “会不会重构”。

而是：

> **第一批 Vulkan / Metal 的 optimizer、densification、loss、GS rasterizer kernels 什么时候填入已经留好的 slot。**

另一方面，Spirula 这次 Partition/ROI 也说明 GS 大场景工具开始摆脱早期的简单思路。它没有只做 spatial tiling，而是在认真处理：

> **谁共同看见什么、边界由谁监督、哪个 Gaussian 最终属于谁、ROI 外为什么不该继续 densify。**

而 Web Renderer 侧，Gaussian-Splat-Lite 与 SuperSplat 已经在进行一场很有意思的路线分化：

> **SuperSplat：尽量去掉排序，再靠 stochastic + temporal reconstruction。**

> **Gaussian-Splat-Lite：保留一个很便宜的 front-to-back 16-bit sort，减少 overdraw，再做 stochastic + TAA。**

接下来真正有价值的不是再看宣传 FPS，而是把这两种路线放在同一台 GPU、同一条 Camera path、同一个 10M+ 场景里，把 **GPU 时间、Temporal Error 和显存**一起画出来。
