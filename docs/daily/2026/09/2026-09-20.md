## gsplat #1062：不是 rasterizer 快了，而是终于发现 B200 在等 PNG

Commit：

`512d366b67073d77ca099ede742683c165dfc23b`

标题非常直接：

> 3DGS training on 8×B200: 13.9 ms → 9.8 ms per step, from decoding one image per step.

新参数：

```bash
--cache_images
```

默认 **关闭**，目前只支持 COLMAP data。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

[gsplat #1062 commit](https://github.com/nerfstudio-project/gsplat/commit/512d366b67073d77ca099ede742683c165dfc23b)

旧路径：

```text
每一步
↓
读取 PNG
↓
decode
↓
undistort
↓
float32 image
↓
Host → GPU
```

新路径：

```text
训练前
↓
4 threads
↓
所有图片 decode + undistort 一次
↓
uint8 保存在 Host RAM

训练时
↓
uint8 Host → GPU
↓
GPU 上 /255 → float
```

所以 Host→GPU 每个像素的传输量理论上从 float32 RGB 的 12 bytes 降到 uint8 RGB 的 3 bytes。

gsplat 当前仓库是 **Apache-2.0**，约 5.7k stars。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

### 这次 benchmark 的口径非常值得保留完整

硬件：

- **8× NVIDIA B200 183 GB**
- 2× Xeon 8562Y+
- CUDA 12.8
- PyTorch 2.9.1
- NCCL 2.27.5

场景：

- Mip-NeRF 360 `garden`
- 161 张训练图
- 1297×840
- SH degree 3

结果：

```text
steady mean step
13.88 ms → 9.78 ms
= 1.42×

median
10.49 → 8.61 ms
= 1.22×
```

GPU peak：

```text
0.95 GB → 0.95 GB
```

Host RAM / rank：

```text
2.51 GB → 2.98 GB
+0.47 GB
```

一次性 cache：

```text
1.44 s / rank
```

。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

### 最关键的限制：完整 wall time 并没有变快

测试只有 875 loop steps：

```text
整个 run
75.7 s → 77.1 s
```

反而慢了约 1.4 秒。

因为整个 76 秒 run 被：

- process launch；
- imports；
- CUDA；
- NCCL startup

主导。

作者估算在该 workload 上：

> 每步省 4.1 ms，约 **350 steps 后才回本**。

默认 30k steps 理论上明显有摊销空间，但**作者并没有给 30k 完整 wall-time benchmark**。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

因此这条正确的表述是：

> **“在 8×B200 的高度 GPU-fast 场景，消除逐步图片解码后 steady step 快 1.42×。”**

而不是：

> “gsplat 训练整体快 1.42×”。

**评级：P1+ / B。**

### 对格式转换尤其重要的是数值语义终于固定

glTF 里：

**Scale 是线性值。**

```text
>= 0
```

不是经典 INRIA PLY 常见的 log scale。

**Opacity 是 0–1 线性 normalized 值。**

不是训练模型常见的 opacity logit。

所以 PLY → KHR glTF 必须类似：

```text
PLY scale log
→ exp()
→ KHR SCALE

PLY opacity logit
→ sigmoid()
→ KHR OPACITY
```

不能原样拷 byte。

Rotation 也按 glTF quaternion 约定；SH degree 0 必须存在，基础 extension 定义到 degree 3。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

### 为什么这对 Metaflow 比“多支持一个格式”更重要

我们以后可以把格式层更明确地划分：

```text
训练 / research
→ PLY

Web streaming
→ SOG / SSOG

轻量交换
→ SPZ

标准 runtime / scene interchange
→ KHR_gaussian_splatting GLB

大型 DCC / VFX
→ OpenUSD
```

而且 GLB 不再是：

> “某个社区 draft”。

它已经是：

> **Khronos ratified KHR extension。**

官方 ratification 同时列出的已知实现包括：

- CesiumJS；
- Cesium Native；
- JSplat；
- `3dgs_ply2gltf`。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

### 注意：这次 Ratification 是基础 GS extension

不能顺带推导：

> 所有 Gaussian compression companion extension 都一起 ratified。

例如 SPZ 压缩相关扩展要单独核其 status。

## 今日结论

今天最重要的不是又一个新的 Gaussian 论文，而是三个“工业化层”的变化同时出现。

**第一，标准层终于需要纠正记录：`KHR_gaussian_splatting` 已经正式 Ratified。** 这意味着 glTF Gaussian 现在有了一个稳定的、厂商共同认可的基础语义，而不再只是互相试验的 draft。

**第二，SuperSplat Viewer 正从“可嵌入 Viewer”继续变成“真正可编程 Viewer component”。** #302 给出来的 seek、walk、movement、annotation、XR API，正是 Metaflow 要减少 DOM hack 和深 fork 所缺的一层。

**第三，训练和产品化都开始围绕“复用已有工作”优化。** gsplat 在复用已解码图像，Spirula 在复用已有 Gaussian，LichtFeld 在保证编辑后的 SOG 和项目写入一致性，Niantic 则在复用同一份 geometry 生成不同光照条件。

整体趋势已经非常明显：

> **3DGS 生态正在从“训练一个漂亮模型”转向“标准化资产 + 可编程运行时 + 可恢复项目 + 可增量训练 + 可配置现实场景”。**
