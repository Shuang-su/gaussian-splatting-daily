## 2. SuperSplat / PlayCanvas 工具链

### P1+：Engine #9584 是今天最需要关注的变化

PR：

[PlayCanvas Engine #9584](https://github.com/playcanvas/engine/pull/9584)

Merge commit：

`72626a18c09499175ec9efadfdb7f6e4e8d7365a`

此前 PlayCanvas 的 streamed GS LOD 最近经历过：

```text
distance-based
      ↓
error / distance selectable
      ↓
今天：
重新统一为 distance-only
```

新模型为：

```text
每个 GSplat
│
├─ lodBaseDistance
│    第一档 LOD 切换距离
│
└─ lodMultiplier
     后续切换距离按几何级数增长
```

默认：

```text
lodBaseDistance = 5
lodMultiplier   = 3
```

并根据 Camera FOV 做补偿。

### 更关键的是预算语义拆成两种

新增：

```text
GSPLAT_BUDGET_TARGET
GSPLAT_BUDGET_LIMIT
```

**Target：**

```text
距离决定初始 LOD
↓
如果总 splat 没达到 budget
↓
继续加细节直到尽量填满预算
```

**Limit：**

```text
距离决定需要的 LOD
↓
如果总 splat <= budget
→ 不强行加细节

如果 > budget
→ 才向下降级
```

这个差异对“远处只有一个资产”的场景很重要。

以前 target-like 策略可能会因为：

> 还有 4M budget 没用完

而把一个很远的环境 GS 继续拉到很高精度。

`limit` 则允许：

> 远就是远，不因为 GPU 还有预算就浪费带宽/显存。

### API 有真实 breaking-like 变化

以下接口不再生效：

```text
GSplatParams#lodMode
GSplatComponent#lodFalloff
GSPLAT_LODMODE_ERROR
GSPLAT_LODMODE_DISTANCE
```

改为：

```text
GSplatParams#splatBudgetMode

GSplatComponent#lodBaseDistance
GSplatComponent#lodMultiplier
```

而：

```text
splatBudget = 0
```

现在明确表示：

> **禁用 budget。**

过去非正数会被替换成默认 1M。

GitHub 的公开 API bot 给出了：

> **+10 / −8 public API surface**

所以如果现有 WebGS 应用直接操作了 `lodFalloff` / `lodMode`，升级 Engine main 前必须迁移。

### LOD allocator 本身也重写

现在通过：

> **“各节点在哪个距离发生 LOD 切换”的 histogram**

分配预算，而不是随着 budget 大小线性增长计算量。

作者测得：

> **典型 budget 下 allocator 约 1.3–2.5× 更快。**

注意这是：

> **LOD allocator 本身**

不是整帧渲染 FPS 提升 1.3–2.5×。

**证据等级：B。**

### #9586：#9584 合入后一小时就修了一个大场景边界条件

PR：

[PlayCanvas Engine #9586](https://github.com/playcanvas/engine/pull/9586)

Merge：

`d02d89453c7003d3358b4d212b1b9343c26aa793`

#9584 会把异常巨大的 LOD node 的距离向 node 中心靠近，避免：

```text
一个巨大天空 / sparse node
最近 corner 离 Camera 很近
↓
整个巨大 node
被误认为近景
↓
加载过高 LOD
```

问题是最初的实现：

> **所有 node 都 shrink。**

如果城市大场景本来就由：

```text
~128 m 的大 chunks
```

组成，Camera 站在某 chunk 内时，连本地 chunk 也可能被“向中心收缩”后判断成远距离：

```text
Camera 正站在该 chunk
↓
错误掉到 LOD 3
```

新实现先统计 octree 中：

> 每个轴上的 **median half extent**

只有超出“典型尺寸”的那部分才 shrink。

作者给出的回归例：

> 128 m 网格中 Camera 所在 chunk 从错误 LOD 3 恢复为 LOD 0。

per-node runtime cost 没增加，因为 excess size 在 octree load 时只算一次。

对城市级 Streamed SOG，这个修复和 #9584 应当视为**同一个 LOD 重构事件**。

## 4. SplatTransform 3.7.0：可以真正指定 Dawn 后端

npm 当前已经是 **3.7.0**，发布时间在本轮窗口内。[NPM](https://www.npmjs.com/package/%40playcanvas/splat-transform?activeTab=dependents)

PR：

[SplatTransform #334](https://github.com/playcanvas/splat-transform/pull/334)

Merge：

`af33a7479e48453db81f0c14d7257e51ecf5f65c`

新增：

```text
--gpu-backend vulkan
--gpu-backend d3d12
--gpu-backend metal
```

例如：

```text
splat-transform \
  --gpu-backend vulkan \
  -g 0 \
  input.ply output.sog
```

这会同时作用于：

- adapter enumeration；
- GPU index；
- device creation。

### 为什么不是一个小 CLI 参数

Windows 中同一张卡可能被 Dawn 列两次：

```text
RTX 5090 — D3D12
RTX 5090 — Vulkan
```

过去：

```text
-g 1
```

主要靠 adapter name 决定设备，同名 backend 可能最终仍落回 D3D12。

现在：

```text
--gpu-backend vulkan
```

先把候选集限定到 Vulkan，再进行 `-g` 选择。

所以：

> **D3D12 vs Vulkan 的性能/稳定性 A/B 终于可以可靠做。**

若指定机器不存在的 backend：

```text
--gpu-backend vulkan
```

不再出现 obscure `TypeError`，而是：

```text
No GPU adapter found for backend 'vulkan'
```

### 上游验证

作者已经在：

> **M4 Max / macOS**

验证：

```text
--gpu-backend metal
```

能正常 GPU render。

`vulkan` 在该 Mac 上不存在，会正确报错。

但：

> **Windows 尚未由该 PR 作者实际验证。**

所以 Windows RTX 的 Vulkan/D3D12 benchmark 值得我们自行跑。

### Gaussian-Splat-Lite：shader varying 24→16 bytes

Commit：

`53ac5da8b69e95319e1ca3eb7e76a96a544473bf`

[Gaussian-Splat-Lite commit](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/53ac5da8b69e95319e1ca3eb7e76a96a544473bf)

当前正式 package 仍显示：

**1.1.7 / Apache-2.0**

这项是 main 新 commit。

每个 splat vertex→fragment varying：

```text
24 bytes
↓
16 bytes
```

布局变成：

```text
RGB
→ FP16

kernel power
→ FP16

alpha
→ FP32

support radius²
→ FP32
```

同时 fragment：

```text
先 support-radius reject
↓
算 alpha
↓
stochastic / coverage reject
↓
最后才 unpack RGB
```

减少那些最终会被 discard 的 fragment 做无效工作。

代价也写得很清楚：

- RGB 上限 clamp 到 65504；
- kernel-power FP16 rounding 可能轻微改变 very-wide kernel coverage。

**没有上游 GPU frame-time benchmark。**

因此只评级：

**P1- / B**

而不能写成“性能提升 X%”。

## 8. Compression / Format / LOD / Streaming

今天没有新的：

- `KHR_gaussian_splatting`
- SPZ spec
- SOG schema
- MPEG GSC
- OpenUSD Gaussian

标准状态变化。

但 **PlayCanvas Engine #9584 是本轮最重要的 LOD policy 变化**。

从工程上看，Streamed SOG 现在更清楚地分成两层：

```text
Asset 层
octree
multi-LOD SOG chunks

Runtime policy
distance bands
+
target / limit global budget
```

这比此前：

```text
error metric
+
distance
+
falloff
+
budget
```

混合决定更容易预测。

对大型实景平台我会更倾向测试：

```text
limit mode
```

# 今日结论

今天最重要的变化，是 **PlayCanvas 的 streamed Gaussian runtime policy 又向“更可预测”迈了一步。**

此前 LOD 系统越来越复杂：

```text
error metric
+
distance
+
falloff
+
global budget
```

现在 #9584 又收敛回：

```text
明确的 distance bands
+
明确的 target / limit budget
```

这对产品开发反而是好事：**LOD 为什么升、为什么降、为什么加载更多数据，变得更容易解释和调试。**

同时 stochastic 路线也跨过一个实际门槛：SuperSplat Viewer 1.36.0 已经不只是“有一个实验 renderer”，而是开始解决 4K history memory、sky/far-plane correctness、near-plane reprojection、debug/benchmark 等真正阻碍产品化的问题。npm 已确认 1.36.0 正式公开。[NPM](https://www.npmjs.com/package/%40playcanvas/supersplat-viewer?activeTab=code)

SplatTransform 3.7.0 则补上了非常实用的一层：**同一个 GPU 上究竟跑 Vulkan、D3D12 还是 Metal，现在终于可以显式决定，而不是让 Dawn 自己猜。** npm 当前也已确认 3.7.0。[NPM](https://www.npmjs.com/package/%40playcanvas/splat-transform?activeTab=dependents)
