# 2. SuperSplat / PlayCanvas 工具链

## PlayCanvas #9532：先检查你的 GS 项目有没有无意中开 4×MSAA

PR #9532 的问题很直接：PlayCanvas GraphicsDevice 如果创建时没有显式：

```text
antialias: false
```

backbuffer 默认可能走 **4× MSAA**。

普通 mesh 未必立刻暴露问题，但百万 Gaussian 每个 fragment 被多采样后成本非常可观。上游实测：

```text
Apple M4 Max
WebGPU
1920 × 1080
3M drawn splats
GPU sorting
```

结果：

```text
4× MSAA backbuffer : 29 ms
single-sampled     : 7.7 ms
```

约 **3.77×** 的 forward-pass 差距。

现在 debug build 会在 Gaussian layer 渲染进 multisampled target 时主动 warning，并建议：

```text
GraphicsDevice:
antialias: false
```

或：

```text
CameraFrame.rendering.samples = 1
```

。[PlayCanvas Engine PR #9532](https://github.com/playcanvas/engine/pull/9532)

这不是 renderer 本身提速，而是阻止一个非常容易踩中的配置陷阱；性能数字有明确 GPU、分辨率、splat 数和 backend，可信度 **B**。

## #9531：Orthographic Camera 的 SH 颜色过去从数学上就错了

普通透视 Camera：

```text
每个 Gaussian
↓
view direction =
Gaussian → Camera Position
```

这是合理的。

但正交相机所有 rays 是：

> **平行的。**

过去 PlayCanvas 仍使用：

```text
Gaussian → Camera Position
```

去算 SH，因此两个很不合理的现象会出现：

```text
正交 Camera 沿 forward 方向平移
→ 图像几何完全没变
→ Gaussian 颜色却变化
```

甚至同一张正交 view 的画面不同区域，会因为 Gaussian 到 Camera 位置方向不同而呈现不同 SH color。

现在：

```text
Orthographic
→ 所有 Gaussian
→ 使用 camera forward 作为 SH direction
```

同时：

- pan / dolly 不再重新算所有 SH；
- rotation 超过 `colorUpdateAngle` 才 refresh；
- perspective ↔ orthographic 切换会强制刷新。

[PlayCanvas Engine PR #9531](https://github.com/playcanvas/engine/pull/9531)

对以下场景特别重要：

```text
Top-down map
Elevation / façade view
Mini-map
Orthographic editor camera
GIS inspection
```

**P1 / B。**

## #9533 / #9535 / #9536：GS 生命周期今天连续补了三个洞

### #9533：销毁 Camera 后 streaming tick 还在访问它

旧逻辑中 LOD streaming 会记住上一帧注册过的 camera。

如果 script update 中：

```text
camera entity.destroy()
```

streaming tick 可能先于下一次 rendering reconciliation 运行，然后访问：

```text
camera.fov
```

于是：

```text
TypeError
↓
LOD tick 失败
↓
autoRender=false 时每隔若干帧继续报错
```

甚至某些 scene switch 会进入持续异常状态。

现在 streaming 会先验证 CameraComponent 是否仍存在。[PlayCanvas Engine PR #9533](https://github.com/playcanvas/engine/pull/9533)

### #9535：Camera 移除 GS layer 后再加回来，GS 过去可能永久不显示

例如：

```text
camera.layers.remove(GS_LAYER)
...
camera.layers.add(GS_LAYER)
```

过去 layer 回来，但 Gaussian placement 不一定重新建立，直到该 GS layer 以后发生别的变化才刷新。

现在：

> Camera 每次开始渲染某个包含 splat 的 layer 时，都会保证该 layer 的 GS rendering 被建立。

[PlayCanvas Engine PR #9535](https://github.com/playcanvas/engine/pull/9535)

### #9536：`frame:ready` callback 内改 GS 状态过去会丢

以前：

```text
frame:ready
↓
enable GS
disable GS
add GS
```

在同一帧内部修改 placement 时，部分相机已经处理过 world state、部分还没处理，结果可能：

```text
Camera A 看旧状态
Camera B 看新状态
下一帧又把改动覆盖
```

现在改为：

> `frame:ready` 内产生的变化在下一帧统一作用于所有 Camera。

[PlayCanvas Engine PR #9536](https://github.com/playcanvas/engine/pull/9536)

### 对 Metaflow 的意义

这三条和前两天的 #9522 放一起看，明显是在集中 harden：

```text
SPA route change
Viewer destroy/recreate
Camera mount/unmount
Layer enable/disable
Scene swap
多 Camera
```

这正是长期宿主应用比官方单页面 Demo 更容易遇到的问题。

## 为什么 Metal 对 Apple Silicon 有实际意义

Vulkan 路径在 Mac 上实际是：

```text
LichtFeld
↓
Vulkan
↓
MoltenVK
↓
Metal
```

新路径变成：

```text
LichtFeld
↓
Metal 4
```

Storage 直接使用：

```text
MTLBuffer
+
Unified Memory
```

host transfer 在 GPU 完成相关 batch 后可以直接 memcpy。

上游在 **Apple M5 Max / macOS 26** 做同一套 API microbenchmark：

| 操作 | Vulkan/MoltenVK | Metal |
|---|---:|---:|
| 1M add | 0.193 ms | **0.164 ms** |
| 1M exp | 0.196 ms | **0.158 ms** |
| 1M transpose | 0.242 ms | **0.159 ms** |
| 16M transpose | 2.355 ms | **0.483 ms** |
| 100 × 4K dispatch | 1.421 ms | **0.261 ms** |

尤其：

```text
100 dispatches
≈ 5.4×
```

的差距主要来自 submission path，而不是算术吞吐本身。

但这些是：

> **Tensor microbenchmarks**

不是：

> “完整 GS training 提速 5×”。

这一点不能混用。

**证据：B。**

# 8. 新开源项目：C³Splat

新仓库：

[C³Splat GitHub](https://github.com/dongjiazhen89/C3Splat)

初始 commit：

`2882be343f7054d62290c4f1987888414ead42b2`

时间：

**2026-09-25 16:20 UTC**

许可证：

**MIT**

它基于 CodecSplat，但解决的是 feed-forward GS compression 中一个容易忽略的问题：

```text
View 1 latent
View 2 latent
View 3 latent
...
```

已有方法通常：

> 每个 view latent 独立 entropy code。

然而多个 camera 实际看到大量相同场景内容。

C³Splat 改成：

```text
已解码 Reference View
        ↓
Depth + Camera Geometry
        ↓
warp 到当前 View
        ↓
按 spatial reliability 聚合
        ↓
成为当前 latent 的 entropy condition
```

也就是：

> **Cross-view causal compression。**

README 报告在 **DL3DV Benchmark、8 input views** 上：

> PSNR BD-rate 相较目标 SOTA baseline 为 **−21.82%**。

这是作者实验值，目前没有独立复现。

### 可运行性

它不是空 repo，包含：

- Stage 1 training；
- Stage 2 rate-distortion fine-tuning；
- arithmetic bitstream evaluation；
- 5 组 main / ablation experiments。

环境：

```text
Python 3.10
PyTorch 2.9.1
CUDA 13.0 example
```

训练脚本示例使用：

```text
CUDA_VISIBLE_DEVICES=0,1,2
```

但仓库**不自带自己的 model checkpoint**。

需要先下载：

## COSA-GS：今天最值得看的论文+代码压缩路线

论文：

**Towards Practical Compression of 3D Gaussian Splatting**

arXiv：

**2609.30245**

提交时间：

**2026-09-24 17:57 UTC**。[COSA-GS 原论文](https://arxiv.org/abs/2609.30245)

官方代码已经可访问：

[COSA-GS GitHub](https://github.com/pengpeng-yu/COSA-GS)

这篇我认为比单纯再提高一点 RD curve 更值得看，因为它瞄准的是一个生产问题：

```text
Encoder 上算出 entropy symbols
↓
传到另一平台
↓
Decoder 浮点 context inference
出现微小数值差异
↓
概率区间改变
↓
entropy decoding 直接错位
```

也就是说：

> 压缩方法论文里“平均 bitrate 很好”，不代表它真的能稳定跨平台解码。

COSA-GS 采用：

- anchor-wise causal factorization；
- 不做复杂 3D spatial aggregation；
- quantization-aware training；
- **integer context inference**；
- bit-exact entropy symbols。

训练依赖：

```text
Python 3.10
PyTorch 2.9.1
CUDA 13 example
CUTLASS
custom RANS coder
```

并可真正输出：

```text
scene.bin
```

然后走：

```text
decompress_and_evaluate
```

从 bitstream 解回来。

**这条值得加入固定 compression 监控。**

## PlenoCI：变化检测不是比较 Gaussian primitive

**PlenoCI: Plenoptic CharacterIstics for View Dependence Aware Change Classification**

```text
分别训练两个 3DGS
```

即使真实环境没变化：

> Gaussian position / count / shape 也不会完全一样。

所以直接：

```text
primitive ↔ primitive compare
```

会产生大量假变化。

PlenoCI 改为比较：

> 这些 Gaussian 集合共同逼近的 **plenoptic field**。

并解析计算：

> plenoptic derivatives。

作者称在“完全没发生真实变化的独立重建”之间：

> false positive 减少两个数量级。

如果以后做：

```text
同一建筑
今天扫描
vs
一个月后再扫
```

这种 change detection，它比对 Gaussian ID 明显更合理。

论文/project/data 已公开，但不是直接生产工具：

**P2+。**

# 今日结论

今天最值得记住的是两个方向。

**第一，Apple Silicon 的 GS 工具链开始出现真正 native Metal backend。** LichtFeld #2436 现在还只有 49/113 个 Tensor GPU ops，不应误报成“完整训练已经 Metal 化”；但它把最难跨过去的架构门槛——GPU storage、command submission、fusion、reduction、统一内存同步——已经搭起来了。

**第二，PlayCanvas 正在快速把 Gaussian 当作真正长期运行的 Engine primitive 来 harden。** 今天修的不再是“Gaussian 能不能画”，而是：

```text
正交 Camera 的 view-dependent color 对不对
默认 MSAA 会不会把性能打掉 4 倍
Camera 被销毁后 streaming 会不会崩
Layer 移除再加回来会不会永久丢 GS
Frame callback 中改状态会不会多 Camera 不一致
```

这些全部是生产环境才会集中暴露的问题。

压缩研究同样出现一个明显趋势：**C³Splat 在利用跨视角冗余，COSA-GS 在解决跨平台 bit-exact decoding。** 研究目标已经从“压得更小”进一步转向：

> **如何让 GS 压缩真正可传输、可解码、可跨平台、可集成。**

对现阶段工具链而言，我会优先做：**LichtFeld Metal backend 试跑 → PlayCanvas 1×MSAA/正交 SH 核验 → SPA Camera/Layer 生命周期压力测试。**
