# 5. 一个有意思的架构决定：它没有用 CUDA selection kernel

原设计本来打算：

```text
Selection
→ Slang compute
→ Vulkan / CUDA 两套 backend
```

实际实现改成：

```text
Selection gesture
       ↓
CPU / OpenMP
       ↓
project Gaussian / vertex
       ↓
selection weights
```

理由是：

- selection 是 gesture commit 时做一次，不是每 frame；
- 同一份代码能处理 Gaussian / point / mesh；
- 不需要 Vulkan/CUDA kernel parity；
- 编辑结果只需要上传少量 attribute array。

例如 Gaussian soft-delete：

```text
opacity
↓
设到 renderer alpha threshold 以下
```

selection tint：

```text
features_dc
```

。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

这对 Metaflow Editor 很值得参考：

> **不是所有百万点编辑操作都值得直接写 GPU compute。**

如果 CPU SIMD/OpenMP 已经足够交互，统一实现可能比维持 GPU 后端更划算。

## 旧逻辑的问题

训练启动时过去会：

```text
整个 dataset
      ↓
遍历所有图片
      ↓
decode / processing
      ↓
canonical JPEG cache
      ↓
全部结束
      ↓
训练 step 1
```

因此：

\[
T_{\text{start}}\propto N_{\text{images}}
\]

几千图的数据集，即使 GPU 已经 ready，也得先等完整 dataset preprocessing。

---

## 新逻辑

现在变成：

```text
Dataset open
     ↓
bounded prefetch window
     ↓
开始 training
     ↓
后续图片
按需要准备 / cache
```

同时，如果原始输入本身已经是：

```text
JPEG
+
不需要 resize / undistort / processing
```

就直接使用原 JPEG encoded data，不再：

```text
decode
→ re-encode JPEG
```

一遍。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

# 20. 今天最值得实际测试的 3 项

## ① Spirula v2026.9.20：重点测 adaptive video extraction

建议用同一段高帧率、高分辨率 capture video，对比：

```text
固定抽帧
1 fps
2 fps
5 fps

vs

Spirula adaptive extraction
```

记录：

```text
输出帧数
↓
COLMAP registered images
↓
matching time
↓
SfM reprojection error
↓
GS training time
↓
最终 PSNR / LPIPS
↓
floaters / geometry quality
```

最值得回答的问题不是：

> “adaptive 少抽了多少帧？”

而是：

> **在相同重建质量下，它能少掉多少重复图片和后续计算。**

如果表现稳定，这可以直接进入以后的视频采集 preprocessing 流程。

---

## ② LichtFeld #2253：用 3k–10k JPG 真正测 time-to-first-step

准备例如：

```text
500 images
3000 images
5000 images
10000 images
```

比较：

```text
#2253 前
vs
#2253 后
```

记录：

```text
dataset open
first training progress
first optimizer step
host RAM
disk reads
```

尤其要区分：

```text
startup latency
```

## 今日结论

今天最明显的趋势不是渲染性能，而是 **GS 工具的“软件工程成熟化”**。

LichtFeld #2253 说明，大规模训练的瓶颈正在从 CUDA rasterizer 转到：

> **JPEG、IO、prefetch 和 dataset lifecycle。**

而 #2254 说明：

> **一个 600MB+ 的 GS project 不应该因为换张 thumbnail 就重写整个文件。**

Spirula 的变化则更值得长期盯：它在同一天从 reconstruction tool 继续向：

> **GS Editor + Project workflow + Agent-controllable GUI**

扩张。

尤其是这套：

```text
统一 Selection
+
operation history
+
splat / point / mesh 共用 editing model
+
MCP GUI automation
```

和 SuperSplat Viewer #302、LichtFeld MCP 放在一起看，趋势已经很清楚：

> **下一阶段的 Gaussian 工具竞争，不只是“谁渲染快”，而是谁能把 capture、training、editing、project state、automation 和 Agent control 组织成一个可靠的完整工作流。**
