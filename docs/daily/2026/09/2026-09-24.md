# 5. PlayCanvas Engine：GS 渲染正确性今天连补三处

## #9493：GPU Sort 的浮点精度问题

Commit：

`dce9f2f99b050d3d6766225d5dce43e78f6a989b`

过去 GPU sorter 大致会先把完整距离映射到：

```text
0 ... numBins
```

的一个 `float32`。

问题在于：

> 当整个 scene depth range 很大，而你真正关心的是 camera 附近两个 Gaussian 很小的深度差时，前面的归一化会吃掉有效尾数。

源码注释甚至直接指出：

> 旧路径在某些范围只有大约 `2^-19` 的有效精度。

现在改成：

```text
先算 Gaussian 相对 Camera 的距离
        ↓
确定 bin
        ↓
再计算 bin 内 fraction
```

也就是 camera-relative precision。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

这对以下场景很重要：

```text
巨大城市 GS
+
camera 附近很密的 facade / railing / foliage
+
far range 很长
```

否则前景排序可能由于 precision collapse 出现透明合成错误。

同时：

- normal depth sort；
- radial sort

都重写了相应 fraction 逻辑。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

**P1 / B。**

## #9490：WebGPU Shadow 中细长 Gaussian 方向可能反了

Commit：

`6ade8a8d6f2cca887899138ccb9fe9535233a4db`

问题来自：

```text
flipY render target
```

Projection center 会 flip，但 Gaussian footprint covariance 使用：

```text
abs(projection scale)
```

于是：

```text
center 镜像了
Gaussian ellipse orientation 没镜像
```

对各向异性强的 Gaussian，例如针状 splat，会非常明显。

结果是：

> Gaussian 本体一个角度，投在 shadow map 上的影子却是镜像角度。

尤其影响：

- WebGPU directional GS shadow；
- CPU sort；
- GPU sort。

现在 covariance Jacobian 保留 projection scale 的符号。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

官方还加入了一个隐藏视觉回归：

```text
一排不同角度的 needle-shaped Gaussians
+
ground plane
+
directional shadow
```

要求：

> 每条 shadow 都必须和平行的 Gaussian 本体方向一致。

这是很好的 renderer regression test。

## #9495：Fisheye GS 在 flipped target 中也有同类问题

Commit：

`9fe0d04fd7fd9a654280c3fe27c43b52d59a637b`

Fisheye projection 自己绕开了普通 projection matrix，因此：

> 普通 renderer 负责的 `flipY` 没有自动作用到 fisheye GS。

后果是：

- fisheye splats 上下颠倒；
- infinite fisheye sky 甚至可能完全不画；
- 超过 180° FOV 时，用 projection `[1][1]` 符号推断 flip 还会误判。

现在新增明确的：

```text
projectionFlipY
```

uniform，而不是猜 matrix sign。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

对于：

- panoramic GS；
- 360 viewer；
- cubemap / offscreen target；
- XR / special projection

这条非常值得注意。

# 7. LichtFeld：训练过程中 Viewport 不再和 Trainer “互相卡 GPU”

## #2325

Commit：

`8b8dd46ee812c3df553bd753be5881b83418cdc8`

标题：

**Keep the viewport smooth while training runs**

。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

旧逻辑里 Renderer 和 Trainer 共用 rasterizer GPU scratch memory。

如果 training frame 正在跑：

```text
Viewport 想刷新
      ↓
等待 training GPU work
      ↓
UI 感觉卡住
```

现在设计变成：

```text
Trainer
 ↔
共享 RasterizerMemoryArena
 ↔
Viewport
```

通过：

```text
render handoff token
CUDA event
reservation
```

协调。

### Camera 不动

Viewport 保留上一帧画面。

按照训练 preview cadence：

**4 Hz**

刷新，而不是无意义不断抢 GPU。

### Camera 正在移动

策略则变成：

```text
Viewport Frame
↓
Training Step
↓
Viewport Frame
↓
Training Step
```

也就是双方真正轮流。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

3DGS 最大的问题之一是：

> 拍出来的桌子、杯子、椅子，都只是整个 radiance field 的一部分，不能自然拿起来。

φ-RIE 的目标：

```text
原始 GS Scene
       ↓
选一个 object
       ↓
同一个 object identity
同时决定：

A. 哪些 Gaussian 属于物体
B. 原 scene 里哪些要删除
C. 删除后背景哪里要补
D. 生成的 movable asset 如何注册
       ↓
Simulator
```

。[arXiv](https://arxiv.org/abs/2609.26795)

```text

背景移除
背景生成
Simulator placement
```

四步分别做，很容易出现：

- duplicate；
- hole；
- transform mismatch。

它强制这些操作共享同一个 object identity。

在 50 个 ScanNet++ 场景，作者报告：

```text
20 mm matching F1
0.336
→
0.383
```

。[ArXiv TLDR](https://arxivtldr.org/abs/2609.26795)

## 今日结论

今天最值得记住的不是某一篇新论文，而是三件更实际的事。

**第一，AMD ROCm 的 GSplat 生态已经比我们之前判断的成熟得多。** 它已经有官方包、官方硬件矩阵、官方 benchmark 和 AMD 维护分支；这意味着 CUDA 不再是 GSplat 唯一有厂商支持的计算后端。

**第二，SuperSplat Viewer 在极快地从“能嵌入”走向“真正的产品 Viewer”。** 1.32 解决 API，1.33 解决首屏/streaming/collision，1.35 开始解决 POI、遮挡、导览相机行为。对实景导览类产品而言，这批变化比再多一个 shader optimization 更直接。

**第三，LichtFeld 已经越来越像一个完整资产工作站。** 它现在关心的不只是训练质量，而是训练时 GUI 能不能顺畅、项目 metadata 是否会导致 GB 级场景重传、License 是否会在 SOG/SSOG→Project→Gallery 中丢失。

而研究侧最有意思的趋势也与工程侧高度吻合：

> **PlayCanvas 正把 stochastic GS 推向生产；论文则已经开始研究如何给 stochastic GS 做极低开销 temporal denoising。**

如果这两条路线最终汇合，下一阶段 WebGS 的性能突破可能不再来自“更快地排序百万 Gaussian”，而是：

> **干脆不排序，再用稳定的时域重建把随机噪声消掉。** （历史上下文，需复核）
