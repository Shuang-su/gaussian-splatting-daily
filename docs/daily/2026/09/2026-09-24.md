# 2. SuperSplat / PlayCanvas 工具链

## SuperSplat Viewer 1.33.0：首屏不再被 Collision 拖住

`v1.33.0` 于 **2026-09-23 09:49 UTC** 发布，核心是 PR **#306**。[官方 v1.33.0 Release](https://github.com/playcanvas/supersplat-viewer/releases/tag/v1.33.0)、[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

以前 Viewer 初始化实际上存在一个很影响体验的问题：

```text
Splat / SOG 已经够显示
        ↓
但 Collision GLB / voxel 还没到
        ↓
Reveal 继续等
        ↓
用户仍看 Poster
```

维护者实测在模拟 4G 网络下：

- splat：不到约 6 秒；
- collision：约 10 秒。

也就是说视觉场景早已可以显示，却因为碰撞数据把整个 Viewer 卡在 loading。#306 现在把两者拆开：

```text
Splat streaming
       ↓
满足 reveal 条件
       ↓
先显示场景

Collision
       ↓
晚到也没关系
       ↓
动态更新 hasCollision / walkAllowed
```

。[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

这项对大场景 Web Viewer 的实际价值很高。

### Streaming Progress 也重做

过去进度监听器本身注册得太晚，常常：

```text
0%
0%
0%
↓
突然 reveal
```

现在从 streamed SOG node 开始加载就计算：

```text
completed nodes
────────────────────
completed + in-flight
```

进度：

- 单调增加；
- reveal 前最多到 99%；
- 必须确认真正发生过一次 streaming 后才允许 reveal。

同时删掉了多余的：

```text
lod-meta.json prefetch
```

因为 octree parser 后面本来还会重新 fetch 一次。[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

### 一个 API 行为变化必须注意

以前很多宿主可能假定：

```text
state.loaded === true
```

意味着：

```text
hasCollision
walkAllowed
```

已经是最终状态。

**现在不成立。**

官方明确要求宿主监听：

```text
hasCollision:changed
walkAllowed:changed
```

。[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

如果后续把 Metaflow Viewer 升到 1.33+，这一项一定要进兼容性测试。

## 一个很夸张但真实的算法修正：Collision Spawn Search

旧搜索最坏情况：

**8,120,601 probes**

现在直接枚举 Chebyshev shell，且搜索半径调整后：

**7,153 probes**

。[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

这是：

\[
8{,}120{,}601 \rightarrow 7{,}153
\]

不是 10%、20% 的小优化，而是把明显错误的搜索空间遍历方式换掉了。

另外，如果 collision 在玩家已经位于 solid voxel 内时才到达：

> Viewer 不会立刻把 camera teleport 出去。

它会暂时 hold collision，等当前位置合法后再启用；进入 Walk 时 collision 尚未到达，则用当前位置高度生成临时 floor。[官方 PR #306](https://github.com/playcanvas/supersplat-viewer/pull/306)

这是很成熟的 late-resource 处理。

# 5. PlayCanvas Engine：GS 渲染正确性今天连补三处

## #9493：GPU Sort 的浮点精度问题

Commit：

`dce9f2f99b050d3d6766225d5dce43e78f6a989b`

过去 GPU sorter 大致会先把完整距离映射到：

```text
0 ... numBins
```

的一个 `float32`。

问题在于：

> 当整个 scene depth range 很大，而你真正关心的是 camera 附近两个 Gaussian 很小的深度差时，前面的归一化会吃掉有效尾数。

源码注释甚至直接指出：

> 旧路径在某些范围只有大约 `2^-19` 的有效精度。

现在改成：

```text
先算 Gaussian 相对 Camera 的距离
        ↓
确定 bin
        ↓
再计算 bin 内 fraction
```

也就是 camera-relative precision。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

这对以下场景很重要：

```text
巨大城市 GS
+
camera 附近很密的 facade / railing / foliage
+
far range 很长
```

否则前景排序可能由于 precision collapse 出现透明合成错误。

同时：

- normal depth sort；

## 今日结论

今天最值得记住的不是某一篇新论文，而是三件更实际的事。

**第一，AMD ROCm 的 GSplat 生态已经比我们之前判断的成熟得多。** 它已经有官方包、官方硬件矩阵、官方 benchmark 和 AMD 维护分支；这意味着 CUDA 不再是 GSplat 唯一有厂商支持的计算后端。

**第二，SuperSplat Viewer 在极快地从“能嵌入”走向“真正的产品 Viewer”。** 1.32 解决 API，1.33 解决首屏/streaming/collision，1.35 开始解决 POI、遮挡、导览相机行为。对实景导览类产品而言，这批变化比再多一个 shader optimization 更直接。

**第三，LichtFeld 已经越来越像一个完整资产工作站。** 它现在关心的不只是训练质量，而是训练时 GUI 能不能顺畅、项目 metadata 是否会导致 GB 级场景重传、License 是否会在 SOG/SSOG→Project→Gallery 中丢失。

而研究侧最有意思的趋势也与工程侧高度吻合：

> **PlayCanvas 正把 stochastic GS 推向生产；论文则已经开始研究如何给 stochastic GS 做极低开销 temporal denoising。**

如果这两条路线最终汇合，下一阶段 WebGS 的性能突破可能不再来自“更快地排序百万 Gaussian”，而是：

> **干脆不排序，再用稳定的时域重建把随机噪声消掉。** （历史上下文，需复核）
