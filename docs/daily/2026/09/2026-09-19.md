# 2. SuperSplat / PlayCanvas：今天最重要的是 #9443

真正的大变化在 **PlayCanvas Engine**：

### #9443 — Stochastic alpha rendering for GPU-sort GS renderer

Commit：

`b193d3ea9dfa526895f0fc6c6cd8e71891debb0f`

[PlayCanvas Engine #9443](https://github.com/playcanvas/engine/pull/9443)

新增：

```js
app.scene.gsplat.stochastic = true;
```

开启后，WebGPU GPU-sort renderer 从：

```text
Projection
   ↓
Compaction
   ↓
Depth key
   ↓
Radix Sort
   ↓
sortedIndices
   ↓
alpha blend
```

变成：

```text
Projection
   ↓
Compaction
   ↓
直接按 compact order draw
   ↓
stable splat ID
   ↓
dither alpha coverage
   ↓
opaque write + depth write
```

也就是说：

> **整个 radix sort 从 frame 中消失。**

而且不是“sort dispatch 数量减少”，而是只使用 stochastic view 时，**sorter 连对象都不分配**；以后切回 sorted/pick 才 lazy-create。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

## 4. 但 stochastic 不是简单把 alpha 变 0/1

关键设计是：

> **使用稳定的 work-buffer splat ID 作为 dither hash。**

如果只用当前 compact index：

```text

↓

↓

↓
noise pattern 每帧换
↓
强 temporal shimmer
```

而现在：

```text
Gaussian 原始稳定 ID
↓
dither pattern 稳定
```

# 5. 一个很重要的 correctness：Depth Prepass 也必须 stochastic

这不是只改 forward fragment shader 就结束。

因为 stochastic renderer：

```text
visible fragment
→ depthWrite
```

那么 depth prepass 如果还把完整 Gaussian quad 当成遮挡物：

```text
┌───────────┐
│ full quad │  ← prepass 写满深度
└───────────┘
     ↓
forward stochastic holes
却被前面的 quad depth 挡住
```

画面会完全错误。

因此 #9443 的 `PREPASS_PASS` 也应用相同 dither test。

这意味着 Gaussian 可以开始更正常地参与：

- depth prepass；
- world geometry depth；
- 后续 depth-based effects；

而不是只在 transparent overlay 里画。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

# 6. Picking 没有跟着 stochastic

这点设计是对的。

Picking 强制：

```text
stochastic = false
```

保留 sorted depth semantics。

否则：

```text
你点一个 Gaussian
↓
这帧恰好被 dither 掉
↓
pick miss
```

就会造成非常糟糕的编辑/交互体验。

因此：

> **显示可以 stochastic，选择依旧 deterministic / sorted。**

这对 Editor 和 Metaflow POI/picking 都非常重要。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

# 14. 旧方案为什么必炸

传统 tile GS rasterizer：

```text
每个 Gaussian
↓
覆盖很多 tiles
↓
生成
(tile key, gaussian id)
pair
```

如果一帧产生：

```text
> 2.147B pairs
```

即使把 index 改成 int64：

内存也非常夸张。

维护者此前估算仅两套 key/value buffer：

> 约 25 GiB；

连 sort double-buffer 算上接近：

> 50 GiB。

所以不是：

> “换 64-bit 就行”。

# 16. 最关键：这不是近似算法

- truncate intersections；

> **byte-for-byte identical。**

# 35. GS-PI 的路线不是传统 per-scene inverse rendering

经典：

```text
GS
+
lights
+
BRDF
+
geometry
↓
一起 optimization
```

很容易：

```text
material
↔
lighting
```

互相补偿。

GS-PI 改成：

```text
pretrained Gaussian
       ↓
extract point cloud
       ↓
geometry-conditioned
3D diffusion
       ↓
predict PBR attributes
       ↓
short differentiable
rasterization distillation
       ↓
PBR Gaussian asset
```

。[arXiv](https://arxiv.org/abs/2609.19907)

并通过 3D 空间 diffusion 避免 2D 多视图 PBR prediction 常见的：

> view-to-view correspondence mismatch。

# 今日结论

今天最值得记住的是三件事。

**第一，PlayCanvas 的 stochastic GS 已从 SuperSplat 层下沉到 Engine 层。**

这意味着未来：

> **“不排序的 stochastic rendering”很可能成为 PlayCanvas Gaussian 的标准性能路径之一，而不是 Editor 专用 trick。**

**第二，OpenUSD 正开始真正成为 Gaussian 的 DCC interchange。**

现在链路已经可以形成：

```text
Reality Capture / Training
↓
OpenUSD ParticleField3DGaussianSplat
↓
Blender
↓
EEVEE / Cycles
```

这比单纯的 PLY/SPZ 更接近成熟 CG pipeline。

**第三，LichtFeld 开始解决真正的大规模训练硬边界，而不是继续微调 0.x dB。**

`#2188` 很典型：面对 24.98 亿 tile intersections，不是继续 prune、降分辨率或报错，而是把整个 rasterizer 改造成：

> **exact batched execution。**

如果把今天几条连起来看，3DGS 生态正在从“怎样让高斯跑起来”，进入下一个阶段：

> **怎样让它像普通工业 3D primitive 一样具备标准格式、DCC 互操作、超大规模执行、私有资产加载和可预测的性能模式。**
