# 2. SuperSplat / PlayCanvas 工具链

过去这一轮，`playcanvas/supersplat`、`supersplat-viewer`、`splat-transform` **没有超过昨天已报告 #1049 / #301 / #318 的新实质 commit**，所以今天不重复。

真正的新 GS 代码在 **PlayCanvas Engine**：

### #9416 — Skip compute work for cached Gaussian splat shadows

Commit：

`1e6832f983228962732cc3a45293125dd8dc1791`

过去 `GSplatShadowRenderer.cull()` 即使某盏灯的 shadow 已经是缓存状态，仍然会先准备一整套 GS shadow compute 资源，包括：

```text
upload interval metadata
→ 更新 bounds-group transforms
→ 同步 user vertex modify
→ 检查/构建 cull shader
→ GS coarse/fine cull
→ indirect args
```

现在逻辑改成先检查：

```text
needsShadowRendering(light)
+
shadowUpdateOverrides
```

只有至少一盏灯真的需要更新 shadow，才开始共享 preparation；完全缓存的灯直接跳过全部 compute。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

这对实际意义比“少一次函数调用”大，因为 GS shadow 的候选集可能是百万级 primitive。对于：

```text
大静态 Gaussian 场景
+
固定太阳/灯光
+
shadow cache
```

过去虽然 shadow texture 不重画，但 GS caster culling 仍可能产生 compute 成本；现在这部分也能停掉。

测试还覆盖了：

- 全部 cached；
- cached + realtime 混合；
- `THISFRAME` one-shot refresh；
- disabled / invisible lights；
- cascade override；
- splat 数据未 ready。

所以这是一个相当完整的调度修复。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

**实际建议：P1 / B。**

不过它**不会直接让当前 Metaflow Viewer 自动更快**。只有当你们升级到包含该统一 GS shadow 路径的 Engine，并且真的让 Gaussian 参与 shadow rendering 时才有收益。

# 5. Viewer / Editor / Web / Mobile / XR

今天最有价值的 Web 信号不是新 library release，而是一份很扎实的 **Three.js r186 实战报告**。

ICS MEDIA 9 月 17 日发布了完整教程，实际从：

```text
手机 Scaniverse 捕获
→ SPZ
→ SuperSplat 清理
→ Three.js WebGPU
```

跑了一遍。Three.js 原生路径现在可以直接：

```js
const geometry = await new SPZLoader().loadAsync(...)
const splat = new GaussianSplat(geometry)
scene.add(splat)
```

而且原生 loader 已覆盖：

- `.spz`
- `.ply`
- `.splat`
- `.ksplat`

但这一实现当前仅支持 **WebGPURenderer**，不是 WebGLRenderer。[ICS MEDIA](https://ics.media/en/entry/260917/)

更值得关注的是作者实际踩出的两个限制。

### ① 当前没有 LOD / Streaming

Three.js r186 的 native GS 当前会：

> **完整下载并加载整个 Gaussian 文件后再显示。**

没有：

```text
distance LOD
hierarchical chunking
progressive streaming
```

所以小物件非常合适，但大城市/大景区不能因为“Three.js 原生支持了 GS”就推断已经可以替代 Spark / PlayCanvas Streamed SOG。[ICS MEDIA](https://ics.media/en/entry/260917/)

### ② Gaussian 没有正确进入 depth-based postprocessing

作者用一个 cube 和 Gaussian 放在相同焦距位置测试 DOF：

```text
Cube
→ sharp

Gaussian
→ 被当成背景深度
→ 错误变模糊
```

Ambient Occlusion 等依赖 depth buffer 的效果也会遇到同类问题。[ICS MEDIA](https://ics.media/en/entry/260917/)

这对 Metaflow 很重要，因为它说明 Three.js 当前更适合：

> **“把 GS 当普通 WebGPU scene object 嵌入现有 Three.js 产品。”**

而 PlayCanvas/Spark 更适合：

> **大场景流式 GS 本身是核心内容。**

经典 3DGS PLY 的：




现在改成：

```text
文件实际每通道 coefficient 数
```

```text
R/G/B 会读错位置
```

。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

# 10. 研究论文

### P2+ — NormLift

**NormLift: From Lifted Features To Semantic Reliability In 3D Gaussian Splatting**  
arXiv: **2609.18898**  
<!-- arxiv:2609.18898 -->
提交：**2026-09-16 16:35 UTC**。[arXiv](https://arxiv.org/abs/2609.18898)

它解决的是 semantic Gaussian 里一个很现实的问题：

传统做法：

```text
多个 view 的 CLIP feature
↓
weighted average
↓
塞给 Gaussian
```

但 CLIP downstream 往往实际使用：

```text
cosine similarity
```

也就是说 feature 本质更接近单位球面上的方向，而不是普通 Euclidean vector。

NormLift 从这个目标重新推导，得到：

> **L2-normalized semantic back-projection 正好是 cosine alignment 的 closed-form solution。**

更有意思的是，聚合后 feature 的 **norm** 被解释成：

- intra-view consistency；
- inter-view consistency；

的组合，因此可以直接作为：

> **“这个 Gaussian 的语义到底靠不靠谱”**

的 confidence signal。[arXiv](https://arxiv.org/abs/2609.18898)

后续用这个 reliability 做 mode-voting refinement，而不是继续线性平均 CLIP feature。

### 对 Metaflow 的潜在价值

如果以后我们给 Gaussian asset 做：

```text
建筑
门
雕塑
路
店铺
植物
```

这种开放词汇标签，NormLift 的意义在于：

> 不只是产生 semantic feature，还同时产生一个**可解释 reliability**。

这很适合：

- 自动 POI；
- 语义拾取；
- AI 导览；
- 搜索；
- 低置信度区域交给人工复核。

当前我没有在 GitHub 检索到官方 NormLift 仓库，所以分类：

**论文 / 暂无核实代码 / A（论文）。**

真正的新内容来自 **PlayCanvas Engine shadow scheduler**。

### #9423：方向光 shadow culling 只由已调度的 shadow pass 请求

Commit：

`113173b0ee1afa4fbc62b66071747926bcf29a2c`

[PlayCanvas Engine #9423 commit](https://github.com/playcanvas/engine/commit/113173b0ee1afa4fbc62b66071747926bcf29a2c)

之前大致是：

```text
camera 看得到 directional light
          ↓
light castShadows
          ↓
做 shadow caster culling
```

现在变为：

```text
Frame Graph
    ↓
真的创建并启用了 Shadow Pass
    ↓
requestDirectionalShadowCull(light, camera)
    ↓
Mesh culler + GSplatShadowRenderer
才处理这个 light/camera
```

它给 `LightRenderData` 增加 `shadowCullRequested`，用现有 per-light/per-camera render data 记录请求，避免另外分配请求对象。**GSplatShadowRenderer 也会检查相机对应的 directional shadow pass 是否真的被调度，再决定是否进行 Gaussian compute culling。** [原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

这解决了一个很实际的问题：`SHADOWUPDATE_THISFRAME` 之类的一次性更新，如果这一帧实际上没有 shadow pass，就不应该提前被消费，也不应该浪费 GS culling。

### #9428：点光/聚光灯也改成相同模型

Commit：

`45e2cca46015dd0c45ac4674dde506d6a998f7d2`

[PlayCanvas Engine #9428 commit](https://github.com/playcanvas/engine/commit/45e2cca46015dd0c45ac4674dde506d6a998f7d2)

Local lights 新增：

```text
_localShadowCullRequests
```

只有 scheduled local shadow pass 会调用：

```text
requestLocalShadowCull(light)
```

点光灯很有意思，因为一个 omni shadow 通常有 **6 个 cube faces**。现在：

```text
6 个 face passes
        ↓
共享同一 light request
        ↓
caster cull 只做一次
        ↓
6 faces 各自 render
```

而不是 6 次重复决定/准备。测试覆盖 clustered / non-clustered、spot / omni、`THISFRAME`、disabled pass、lightmapper 等情况。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

### 为什么这对 Gaussian 特别重要

Mesh caster culling 本身已经不便宜，但 Gaussian shadow 场景可能有数百万到千万 primitive，需要：

```text
world intervals
→ bounds-group transforms
→ coarse/fine GS culling
→ indirect draw/compute args
```

所以从：

> “灯可见就算一遍”

转到：

> **“这一帧真的有 shadow render pass 才算”**

收益潜力明显更大。

这是 #9416 的自然后续：

```text
#9416
cached GS shadow
→ 不执行无意义 compute

#9423 / #9428
根本没安排 shadow pass
→ 连 caster cull request 都不产生
```

**目前不是立刻升级理由。**

你们当前 Web Viewer 的核心目标还是：

- GS 自身可视化；
- SOG streaming；
- collision；
- 导览；

不是把 Gaussian 当带实时 shadow 的普通游戏几何。

但如果以后加入：

```text

+

+
灯光
+

```

这套调度会越来越重要。

```text

×
existing material transmittance
```

的组合，而不是覆盖/错误组合原材质透明度。

- EEVEE depth；
- shadow；
- transparent material；
- Gaussian + material interaction。

## 今日结论

今天的变化没有 Blender 原生 GS 那种 P0 级爆炸性，但出现了两个很清楚的长期趋势。

第一，**PlayCanvas 正在把 Gaussian 从“特殊 renderer”继续推进成正常 engine citizen**：现在不仅有 sorting、LOD、streaming、stochastic rendering，连 shadow caster scheduling 都开始和普通 mesh 使用同一套 frame-graph/request 生命周期。

第二，机器人方向开始从：

> “GS 是高保真地图”

进一步发展到：

> **“GS 是可以生成机器人 observation/action 数据的可控中间世界”。**

PrecisionReach-GS 就是一个很典型的例子：真正重要的不是它又训练了一个 Gaussian，而是它把：

**现实坐标 → GS → robot frame → camera trajectory → VLA data**
