# 2. SuperSplat / PlayCanvas 工具链

## P1+：Engine #9520 把 Streamed SOG 从 FIFO 加载改成“视觉需求调度”

Commit：

`fe280fdbdc807fb9bf117e01b4d352c0879d07d3`

[PlayCanvas Engine #9520](https://github.com/playcanvas/engine/commit/fe280fdbdc807fb9bf117e01b4d352c0879d07d3)

这是今天对 Metaflow 最值得注意的一项 PlayCanvas 改动。

过去 Streamed SOG 的 chunk 请求更接近：

```text
LOD manager
   ↓
需要 file A / B / C / D
   ↓
依请求顺序排队
```

现在 queue 带明确 priority：

```text
最高优先级
│
├─ 当前可见区域什么都没有
│     → 先把洞填上
│
├─ 当前 LOD 正在等待升级/切换
│     → 尽快完成切换
│
└─ 纯 refinement / prefetch
      → 有空再下
```

在每一个 tier 内，又按：

> **距离相机更近的 node 优先。**

源码定义实际上就是：

```text
VISIBLE  = 2
SWITCH   = 1
PREFETCH = 0
```

因此这不只是“最近优先下载”，而是：

> **语义优先级 > 空间距离优先级。**

这比纯 distance scheduler 更符合用户感知。

---

## 不再需要的请求会从队列撤掉

新的 loader 增加：

```text
dequeue(url)
```

如果相机已经转走，某 chunk：

```text
之前需要
↓
还在等待下载 slot
↓
现在没有任何 camera 需要
```

就不会继续白白下载。

需要准确区分：

> **它能撤销尚未开始的 queued request，并不是通用 HTTP 中途 abort 已开始下载。**

对于：

- 移动网络；
- PICO / Quest；
- 用户快速转头；
- 城市级 Streamed SOG；

这能明显减少浪费带宽的概率。

---

## 多 Camera 也开始共用需求集合

如果：

```text
Camera A
Camera B
```

都指向同一个 octree，request 不再各管各的。

同一 file 的多个需求会汇总，保留其中最高 priority。

这为以后：

```text
主 Viewer
+
缩略预览
+
小地图 Camera
+
Portal / secondary camera
```

共享 Streamed SOG 提供了更合理的底层调度。

同时默认参数也调整：

```text
lodBehindPenalty
1.0 → 1.5

lodUpdateAngle
0° → 90°
```

因此仅仅旋转一点相机不再不断触发完整 LOD update；镜头背后的 node 也会更明显降权。

**评级：P1+ / B。**

# 3. SuperSplat Viewer：Picking 开始和 stochastic renderer 使用相同的透明度思想

PR：

**#311 — Stochastic pick depth, opacity-based annotation occlusion and a pick-depth debug view**

Merge SHA：

`15ceaa340417df2f9bc5e9c9fca44e600e8b9954`

[SuperSplat Viewer #311](https://github.com/playcanvas/supersplat-viewer/pull/311)

以前 picker 对透明 Gaussian 的 depth 更接近：

> alpha-weighted depth average。

问题很容易理解。

假设：

```text
Camera
 ↓
薄雾 Gaussian
 ↓
薄雾
 ↓
薄雾
 ↓
真正墙面
```

如果把多个透明 layer 的 depth 做加权平均：

```text
pick depth
```

可能跑到：

> 空气中某个位置。

这会影响：

- Click navigation；
- POI；
- Annotation occlusion；
- Walk / camera target；
- “点墙却飞到墙前面”。

---

## 新实现：4 次 stochastic survival trial

每个 Gaussian fragment：

```text
以 opacity 作为存活概率
```

每 pixel：

**4 trials**

然后：

```text
MIN blend
```

保留每次 trial 中最靠前的 surviving fragment。

最终 surface depth 定义为：

> 在一个 **2 px disc** 内，前方累积 opacity 达到 **0.3** 时对应的 depth quantile。

同时对每个 splat 使用 stable seed，使：

```text
同一 Camera Pose
同一点重复点击
```

不会因为随机数不断抖动。

这很聪明，因为它开始让：

```text
渲染透明度模型
```

与：

```text
交互 Picking 的“什么算表面”
```

采用相近的概率语义。

---

## Annotation 遮挡也同步重做

旧：

```text
pickMany
```

变成：

```text
pickVisibility
```

一个热点前方 **13 px disc** 内，如果平均遮挡 opacity：

\[
\ge 0.5
\]

就认为它被遮住。

这比：

```text
拿中心 pixel 做一次 depth test
```

对植被、细栏杆、半透明边缘更合理。

还增加了：

**Debug → Pick depth**

可以把“当前所有 pixel 如果点击，会落在哪个 depth”直接可视化。

对开发导览系统特别有用。

### Streaming 下的代价

上游也明确写了：

> Streamed detail 尚未稳定时，pick cache 每帧 invalid。

所以打开 Pick Depth debug 时，在 streaming 结束以前可能会每帧都重画这个 pass。

这是调试功能，生产时通常不会打开。

## #310：Annotation 被选中后，Orbit pivot 终于落到“物体”附近

Merge SHA：

`24959485cb8e3a3e9f705a8465a4a523bde8d3ee`

[SuperSplat Viewer #310](https://github.com/playcanvas/supersplat-viewer/pull/310)

真实项目里 authored annotation target 很可能：

- 离镜头只有 1.5 cm；
- 穿过主体；
- 在主体后面很远。

过去从 annotation camera 进入 Orbit 后：

```text
Orbit
围绕 authored target
```

于是 camera 一拖就飞。

现在会计算：

```text
annotation.position
沿当前 view direction 的 depth
```

并把 orbit focus 放在相同 view ray 上的这个深度。

**原本 annotation camera pose 完全不改变，改变的只是之后 Orbit 的 pivot。**

这对实景导览属于非常“产品型”的修复。

# 4. PlayCanvas #9522：GS Entity 销毁后逐帧报错的问题修掉

Commit：

`408dd7ca252470258b130f7c9f7c3ff2d3a9a902`

[PlayCanvas Engine #9522](https://github.com/playcanvas/engine/commit/408dd7ca252470258b130f7c9f7c3ff2d3a9a902)

这是一个典型 SPA 生命周期 bug。

执行：

```text
destroy GS entity
```

后，render layer 里的旧 placement 并不会在完全相同的时机马上 reconcile。

但 GS streaming tick：

```text
framerender
```

可能先执行。

于是：

```text
cached placement
仍存在

resource
已经 null
      ↓
world-state rebuild
读取 null
      ↓
throw
      ↓
本帧 render 被中断
      ↓
正常 reconcile 永远没有机会执行
      ↓
下一帧继续 throw
```

变成**永久逐帧错误循环**。

现在 `GSplatWorld.update()` 会提前清除：

```text
resource == null
```

的 standalone placement。

对以下场景很实用：

- React/Vue route change；
- Viewer destroy/recreate；
- 模型切换；
- 多个 GS asset dynamically mount；
- Metaflow 资源浏览器。

**P1 / B。**

# 5. Compression / Format：LichtFeld 正式接入 Khronos glTF Gaussian

这是今天整个生态层面最重要的新变化。

PR：

**#2344 — glTF/glb splat IO support**

Merge SHA：

`0d8e921893dc4dadbe8e91a4c4dadf8618b0984e`

合并时间：

**2026-09-25 04:26 北京时间左右。**

[LichtFeld Studio PR #2344](https://github.com/MrNeRF/LichtFeld-Studio/pull/2344)

现在 LichtFeld 可以读写：

```text
.glb
+
KHR_gaussian_splatting
+
KHR_gaussian_splatting_compression_spz_2
```

这是很大的互操作进展。

基础 `KHR_gaussian_splatting` 已经正式 Khronos Ratified。[GitHub](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)

而 `KHR_gaussian_splatting_compression_spz_2` 当前仍应视为**伴随压缩扩展的 draft 路线**；不要因为基础 extension 已 Ratified 就把 SPZ_2 的状态一并写成 Ratified。当前公开生态文档仍明确把 SPZ_2 标为 draft。[GitHub](https://github.com/spz-ecosystem/spz2glb)

---

## Import：GLB 不再默认等于 Mesh

新的分流：

```text
.glb
 ↓
是否包含 GS / SPZ Gaussian extension？
       │
       ├─ Yes → Gaussian
       │
       └─ No  → 原 Mesh GLB loader
```

所以普通 GLB Mesh 行为不变。

Gaussian GLB 导入还会：

- 应用 node matrix；
- 按 3D Tiles 约定处理 Y-up → LichtFeld Z-up；
- 遇到 `lin_rec709_display` 时转换到 sRGB；
- 解出 SPZ 数据后生成正常 GS model。

这对 GIS / Cesium 特别关键，因为 geospatial Gaussian 很少保证 asset 就在：

```text
origin = 0
rotation = identity
```

---

## Export：PLY 可以直接变 Khronos GLB

现在 CLI 可：

```text
convert scene.ply scene.glb
```

也可通过：

```text
mesh2splat
--export glb
```

输出。

写入包括：

- `kernel`
- `colorSpace`
- `OPACITY`
- SH0
- higher SH `VEC3`
- Rotation / Scale / Position

等 spec 语义。

另外有一个很合理的新变化：

```text
SPZ precision
```

不再硬编码固定量化精度，而通过：

```text
spz::PackOptions::fractionalBits
```

控制。

## 大坐标场景：先 recenter 再压缩

GLB export 会：

```text

   ↓
recenter positions
   ↓

   ↓

```

这对：

- ECEF；

- 城市坐标；
- 远离 origin 的资产

尤其重要。

否则：

```text

+

```

会白白损失局部精度。

# 11. Avatar / Human / Generative / Physical GS

## GaussPDE：把 Gaussian 本身当 PDE 离散域

论文：

**GaussPDE: Graph-Based Partial Differential Equation-Driven Rendering for 3D Gaussian Splatting**

arXiv：

**2609.27264**

<!-- arxiv:2609.27264 -->
提交 9 月 23 日，9 月 24 日更新。[GaussPDE 原论文](https://arxiv.org/abs/2609.27264)

它不是：

```text
GS
↓
转 Mesh
↓
做模拟
```

也不是：

```text
GS
↓
Voxel
↓
网格 PDE
```

而是：

```text
Gaussian primitives
       ↓
构建 active graph
       ↓
Graph Laplacian
       ↓
直接演化 PDE state
```

Graph edge 会考虑：

- covariance-aware distance；
- opacity；
- appearance；
- boundary-aware conductance。

然后 PDE scalar field 通过：

> 修改 DC spherical-harmonic color coefficients

反馈回渲染，同时保持：

- Gaussian geometry；
- opacity；
- view-dependent higher-order appearance。

[arXiv](https://arxiv.org/abs/2609.27264)

可以理解成：

```text
普通扫描 GS
+
热扩散 / 浓度 / 标量场
```

直接做动态可视化。

### 为什么要先 regularize Gaussian

如果 scene 中：

- 相机附近 floaters；
- 超大的 Gaussian；

直接构图，会造成：

```text
错误 graph edge
↓
PDE 沿错误连接传播
```

所以论文在 reconstruction 阶段额外做：

**camera-aware regularization**

保证之后这个 Gaussian graph 真正适合作为 computational domain。

### 代码状态

搜索到官方同名 GitHub：

`Kilow-YUE/GaussPDE`

但当前 repo size：

> **0**

即还没有实际代码。

因此不能写：

> “代码公开”。

正确分类：

**P2 / 论文无代码。**

# 今日结论

今天最值得记住的是 **LichtFeld #2344 + PlayCanvas #9520 + Viewer #311** 这三条。

它们分别解决三个完全不同、但都已经属于“成熟 GS 平台才会碰到”的问题：

```text
资产怎么跨生态
→ Khronos GLB

大场景下一秒应该先下载什么
→ Priority Streamed SOG

透明 Gaussian 里“表面”到底在哪
→ Stochastic Picking
```

这已经不是早期 3DGS 时代那种：

> “能不能把 PLY 画出来”。

另一个明显趋势是，**Spirula Studio 正在快速填补 SuperSplat 和 LichtFeld 之间的空位**：它现在已经同时具备 Capture/SfM、训练、GS/Point/Mesh 编辑、视频输出和 MCP Agent，而且 v2026.9.24 已把这些能力带进正式 Release，而不再只存在于主干实验代码。[Radiance Fields](https://radiancefields.com/spirula-studio-v2026.9.24-adds-editing-and-an-mcp-server)

对于现有 Metaflow 路线，我认为今天最值得吸收的架构可以压缩成一句：

> **Web 交付继续以 Streamed SOG / PlayCanvas 为主，资产互操作开始认真接 Khronos GLB/3D Tiles，而 Editor 和 Agent 层则应该尽可能依赖公开的语义 API，而不是继续扩大 Viewer/Editor 私有 fork。** （历史上下文，需复核）
