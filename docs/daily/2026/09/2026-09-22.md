## #322：景深从“把 Gaussian 膨胀”改成真正采样光圈

旧实现更接近：

```text
一个 splat 失焦
↓
扩大屏幕 covariance
↓
模拟 blur
```

问题是：

> silhouette / 前后遮挡并不正确。

新的实现则：

```text
Lens aperture
  ●  ●  ●
 ●   ●   ●
  ●  ●  ●

每个 aperture sample
↓
独立 camera origin
↓
独立投影 / sorting / visibility
↓
最后平均
```

新增：

```text
--dof-samples
default = 32
```

强失焦可以提高到 64 等。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

更重要的是 DOF 和 motion blur 现在统一在：

> **premultiplied linear light**

里累计，最后才编码回 sRGB。

因此：

```text
高亮
透明边缘
motion blur
defocus blur
```

不会因为每个 sample 先量化/先 gamma blend 而产生明显错误。

但成本也很明确：

```text
总 sample 数
≈ motion_samples × dof_samples
```

比如：

```text
16 motion
×
32 DOF
=
512 renders / frame
```

所以这是**离线质量路径**，不是实时 Viewer 功能。

#322 的验证覆盖了 840 tests；维护者也明确说明 NVIDIA allocation 行为目前是模拟覆盖，而不是此次 PR 中真实 NVIDIA hardware run。[原始聊天工具引用，需补一手链接](https://chatgpt.com/share/6abb77e3-2854-83ee-a59d-1b8d31259f88)

## Cube-Splat：360° Gaussian SLAM 值得加入固定监控

论文：

**Cube-Splat: High-Fidelity 360° Gaussian Splatting SLAM via Cubemap Factorization and Adjoint-Consistent Optimization**

arXiv：

**2609.21347**

提交：

<!-- arxiv:2609.21347 -->
**2026-09-18**。[arXiv](https://arxiv.org/abs/2609.21347)

核心方法不是把 ERP 直接扔进普通 pinhole GS。

它将每一帧 360° 图像拆成：

```text
同一个真实 camera center

Front
Left
Back
Right

4 个固定朝向
cubemap pinhole views
```

但这些 views **共享同一个真实 pose**。

前面我们讨论 Panorama-to-3DGS 时已经强调过：

> 同一光心切多个 perspective view 不会产生新的 translational parallax。

Cube-Splat 没有假装它们是独立相机，而是用 **adjoint-consistent optimization** 把多个 cubemap face 的 pose gradient 正确汇总回同一个真实相机 pose。

Mapping 则把不同 face 的 ray 一起用于 Gaussian reconstruction。

论文还引入 **SynPano** dataset，并报告在：

- PALVIO；
- OmniBlender；
- SynPano

上的结果。[arXiv](https://arxiv.org/abs/2609.21347)

## 今日结论

今天没有 Blender 原生 GS、KHR Ratification 那种 P0，但**PlayCanvas 工具链跨过了一个明显的产品化节点**。

过去几天我们看到的是：

```text
Viewer #301/#302
→ main 上能力已经很好

SplatTransform #320/#322
→ PR 中开始像离线 renderer
```

今天则变成：

```text
SuperSplat Viewer 1.32.0
        +
SuperSplat 3.3.1
        +
SplatTransform 3.5.1
```

**三条同时成为正式 Release。**

对 Metaflow 最直接的意义是，PlayCanvas 这套链路正在越来越清楚地分层：

```text
SuperSplat Editor
→ authoring / camera track

SplatTransform
→ format / LOD / offline rendering / sequence export

SuperSplat Viewer
→ embeddable runtime component

PlayCanvas Engine
→ GS renderer / streaming / stochastic / WebGPU
```

这比继续把“Editor、CLI、Viewer 各自当独立项目”更重要。

而研究侧的 Cube-Splat、厂商侧 AMD-Ecosystem 的 gsplat 动向，则说明另外两条路线也值得继续盯：

> **360° GS-SLAM 正在解决真正的 spherical camera optimization；AMD 生态则似乎正在准备把主流 CUDA GS 工具正式带到 ROCm，但当前公开 GitHub 状态还不足以宣布它已经可用。**
