## 2. SuperSplat / PlayCanvas 工具链

### PlayCanvas Engine：大场景 WebGPU 从“黑屏”退化为“较慢但可见”

[commit d0127b10](https://github.com/playcanvas/engine/commit/d0127b10af116c63b4d3732488b2b8157eebeeb9) 修的是 GPU-sorted splats 的硬上限，而非一般 draw-call 问题。projection cache 以 32 B/splat 占用 storage buffer；当 active splat 数与 varyings 合计超过 `maxStorageBufferBindingSize`，旧路径仍提交无效 GPU draw，部分 128 MiB 上限设备在约 4.19M splats 后直接不显示。

新代码在 draw 前计算 `elementCount × (CACHE_STRIDE + varyings.words) × 4`，超过设备上限时停用 GPU sorter；`GSplatManager` 对对应 camera/layer 生命周期改用 CPU sorting，直到 layer 清空或 camera 停止后重置。对 Editor/Viewer 的影响是超大模型不再静默黑屏；对 WebGPU 的代价是 CPU 排序延迟与主线程压力可能上升。它不改变 SOG/SPZ/PLY、LOD 或 streaming，也未进入 [当前稳定版 v2.23.3](https://github.com/playcanvas/engine/releases/tag/v2.23.3)。**建议锁定该 SHA 做兼容测试，不要把 main 自动升级成生产版。**

### SOG v3：值得做兼容性原型，不能现在切默认格式

[splat-transform issue #362](https://github.com/playcanvas/splat-transform/issues/362) 是维护者公开设计稿：

- rotation 拟从 `quats.webp` 中的 26-bit smallest-three quaternion 改为分布在 means/scales alpha 通道的 24-bit exponential map，移除整张 rotation texture；
- opacity 通过 codebook 支持大于 1 的“质量”，让 decimated LOD 更好保存视觉质量；renderer 需配套 plateau profile；
- SH 从固定三阶扩展为 1–4 阶；
- 可选 `blind.webp` 为每个 Gaussian 保存 1–4 字节应用数据，如 segment/object/selection ID；
- 顶层 `extras` 和 streamed SOG 的 `lod-meta.json` 承载扩展 metadata；PLY 互操作拟增加 `opacity_excess` 与 blind property；
- SplatTransform 计划以 v3 为默认并提供 `--sog-version 2`，但 HTML viewer 在支持前仍使用 v2。

issue 给出的 decimated-scene PSNR 从 19.6→26.3 dB（SplatTransform）和 19.3→25.8 dB（Engine），以及四阶 SH scene 的 35.8 dB；这些是维护者提案中的样例，不是独立 benchmark，缺少统一设备/场景/文件大小口径。今天应做 v2/v3 双读写设计与 golden assets，**不要把提案写成标准已落地**。

固定检查 [SuperSplat](https://github.com/playcanvas/supersplat)、[SuperSplat Viewer](https://github.com/playcanvas/supersplat-viewer) 与 [SplatTransform](https://github.com/playcanvas/splat-transform)：窗口内没有新的 commit、merged PR 或 release；正式版本仍为 SuperSplat v3.7.0、Viewer v1.41.0、SplatTransform v3.10.3。没有新的 Editor selection/histogram、camera path、viewer export 或 WebXR 行为需要单独升级。

## 3. 可实际运行的开源项目

### OOOSplat 0.7.1：从“主线策略”升级为“可下载安装”

[0.7.1 pre-release](https://github.com/ooolabdev/ooosplat/releases/tag/0.7.1) 提供 Windows x64 EXE、Apple Silicon DMG 与 Ubuntu x64 DEB。核心变化是 generation policy 可解释化：Detailed 档同时暴露原始分辨率、effective-pixel ceiling 与 track budget；只有实际 GPU OOM 才允许一次 80% 重试，避免把普通错误误判为显存不足；初始 registration 低于 80% 且存在有效模型时，manual sampling 与最多 20% 的 bridge backfill 可恢复覆盖。

### Spirula Studio：允许直接修掉错误对应关系

[匹配矩阵编辑器](https://github.com/harry7557558/spirula-studio/commit/018f150684f50479ec5121327f66042b20bc72b2) 把 pairwise matches 变成可视化矩阵，可从 map 上下文菜单打开、删除 false matches、自动备份 `matches.bin.bak`、重载 previews，并把模型标记为需要 rebuild；保留 intermediates 便于继续处理。相比“重新调一轮 matcher 参数”，这是对已定位错误 pair 的确定性修复。

[资源预测 commit](https://github.com/harry7557558/spirula-studio/commit/91c93e9019aafa71f12c9199eb39ad884c4c5fe7) 统一了 training/dense/meshing/mapping 的 RAM/VRAM forecast、风险标签与 tail probability；文档样例是作者测量，不应外推为跨 GPU benchmark。当前只有 GPL-3.0 master，没有 v2026.10.16 之后的新 release。

### CTBakeGS：最低门槛的医学体数据浏览器转换器

[CTBakeGS](https://github.com/BocchiSlice/CTBakeGS) 是 MIT、单 HTML、无需服务端；选择 DICOM/NIfTI 后可在浏览器进行自适应 octree conversion，导出 PLY/SPZ。仓库无正式 release，今天核查时活跃度仍很早期；适合验证体数据→splat 的交互与导出，不适合医疗诊断、隐私数据上传或生产归档。

## 5. Viewer / Editor / Web / Mobile / XR

- **WebGPU viewer**：PlayCanvas 的 storage-buffer 上限检查值得在 4M/5M/8M splat 资产、128/256 MiB 绑定上限和多 camera/layer 组合回归。成功标准是场景可见、fallback 状态可解释、切换/清空后能恢复，不只看单帧 FPS。
- **XR**：[LichtFeld OpenXR commit](https://github.com/MrNeRF/LichtFeld-Studio/commit/01367cfc957c68c10eafa35178380f2ec1cc115c) 通过 `XR_KHR_vulkan_enable2`，检查 runtime 与 renderer 使用同一 GPU；双眼 viewport 经 GPU 拷贝进 swapchain，左眼镜像到桌面。若 GPU 不一致会回退桌面。它是 view-only，不能在头显里编辑 splats。
- **浏览器转换**：[CTBakeGS](https://github.com/BocchiSlice/CTBakeGS) 把 DICOM/NIfTI→PLY/SPZ 拉到 Chrome/Edge 本地执行；真实测试要记录浏览器内存、数据尺寸、导出大小和重开一致性。
- **移动端**：[splatkit run.json schema](https://github.com/Xget7/splatkit/commit/90b0cdf7b0b5560b74789fef43c6557fa0dd8e2c) 让 iOS/Android dev apps 与 benchmark scripts 共享类型化配置，未知/错误 key 直接报 `SplatRunInvalid`，并将运行配置与报告并置。它不加快渲染，但提高跨端 benchmark 可复现性。

3. **未见新标准动作**：窗口内未核实到 Khronos glTF Gaussian extension、OpenUSD、3D Tiles、MPEG GSC 或 W3C WebGPU 的新正式规范/批准版本。

SOG v3 的 opacity>1 目标是让 decimation 后的 LOD 保存辐射质量；这会改变 renderer profile 与资产验证口径，不能只比较文件字节数。建议同时记录文件大小、GPU bytes/Gaussian、随机访问、首帧时间、LOD pop、PSNR/SSIM 与 v2/v3 互转损失。

## 7. Training / Reconstruction / SLAM / Robotics / Mapping

### LichtFeld SAM2.1：训练前处理的实质性闭环

[SAM2.1 commit](https://github.com/MrNeRF/LichtFeld-Studio/commit/103636f9ef1f342346dbe2ded117bc647b0b1ff1) 把模型推理集成到 Video Extractor 和 CLI；输出 `images/*.jpg` 与 `masks/*.jpg.png`，0 表示排除、255 表示保留，现有训练 mask loader 可直接读取。自动模式从画面边界纹理 cell 推测 operator seed；也支持 foreground/background 点、box、鱼眼有效圆/重心、0–128 dilation（默认 12）、前后向 tracking，以及连续 3 帧不可靠后的恢复。

[模型资产 release](https://github.com/MrNeRF/LichtFeld-Studio/releases/tag/model-sam2-video-v1) 使用约 323 MB 的永久 `.lfw` 权重，release 被标为 pre-release 只是为了不覆盖应用 Latest badge。运行需要 CUDA GPU。静态相机、人物与背景近似共动、快速遮挡或小目标仍需要手工 seed；应抽查 mask 边缘而不是相信自动模式。

### SLAM 研究：两篇都没有可运行实现

<!-- arxiv:2610.36853 -->
[LingGS（arXiv:2610.36853）](https://arxiv.org/abs/2610.36853) 将 feed-forward geometry prediction 与 camera tracking 解耦，目标是在 Gaussian SLAM 中减少 tracking 误差对几何质量的持续污染。公开 arXiv 页面没有可核实代码、权重或 demo，分类为 P2、论文无代码。

**编辑摘要：** 解耦 tracking 与重建的工程动机成立，但没有实现时无法评估回环、重定位、长序列显存和实时预算，也不能与 gsplat/OpenSplat 的现有训练路径直接集成。

**编辑摘要：** 它把尺度先验和 outdoor chunking 放在 Gaussian SLAM 核心位置，适合追踪地图集成；但“将公开”不等于代码可用，当前不能验证驾驶长序列、动态物体或跨天气稳定性。

## 10. 研究论文

### DomeGS：VR 无界场景的背景补全

<!-- arxiv:2610.37172 -->
[DomeGS（arXiv:2610.37172）](https://arxiv.org/abs/2610.37172) 研究 3DGS 在 VR 大幅转头时暴露未重建背景的问题，以感知一致的 dome/background completion 替代简单 skybox。论文报告 36 人用户研究，在 presence/realism 上相对 skybox 的显著性 p=0.042；未找到公开代码或权重。

**编辑摘要：** 问题与头显自由转动高度相关，感知评测比单纯 PSNR 更有价值；但样本量、场景数和无代码状态意味着现在只能作为 XR 内容策略参考，不能直接进入 viewer 管线。

### GeoGSplat：非 pixel-aligned 的 feed-forward Gaussians

<!-- arxiv:2610.36760 -->
[GeoGSplat（arXiv:2610.36760）](https://arxiv.org/abs/2610.36760) / [项目页](https://comedy0913.github.io/projects/geogsplat/) 以 geometry-grounded anchors 与 triplane 预测固定数量、非 pixel-aligned primitives，并通过层次 dense points/Gaussians 改善大视角变化。项目页存在，但本轮未核实到可运行代码或权重。

**编辑摘要：** 从每像素 primitive 转向几何 anchor 有助于控制 primitive 数与遮挡，但今天仍是论文+演示；需要代码后才能比较 feed-forward 延迟、跨数据集泛化与固定预算下的质量。

### StereoSplat：本轮是版本更新，不是首次发布

<!-- arxiv:2610.35902 -->
[StereoSplat（arXiv:2610.35902）](https://arxiv.org/abs/2610.35902) 本轮更新了以 foundation stereo backbone、cross-view fusion、gated depth 和 learnable inverse-depth aggregation 进行 metric-scale NVS 的论文；同时介绍 XRStereo 合成数据。其首次发布日期早于本窗口，因此只计 arXiv revision，不冒充新首发。

**编辑摘要：** stereo grounding 对 XR 的米制尺度很有吸引力，但没有核实到代码/权重时，无法检查 zero-shot real stereo、相机标定误差和动态场景退化；分类为论文无代码。

### Honeycomb-Surfels：以 Hexels 替代 Gaussian

<!-- arxiv:2610.37668 -->
[Honeycomb-Surfels（arXiv:2610.37668）](https://arxiv.org/abs/2610.37668) / [项目页](https://honeycomb-surfels.github.io/) 提出平面六边形 surfel（Hexel）及一阶空间颜色。论文宣称在 memory-matched 2DGS 上提升 4.53–7.38 dB、最高 2.31× FPS，并降低 28.9% error；项目页尚未提供可运行 release。

**编辑摘要：** 这是本批最接近 primitive 范式变化的条目，但“memory-matched”对照与作者 benchmark 不能外推到所有 3DGS 场景；代码未公开前只做 P2 跟踪。

### CTBakeGS：代码已公开，性能数字需谨慎

<!-- arxiv:2610.37406 -->
[CTBakeGS（arXiv:2610.37406）](https://arxiv.org/abs/2610.37406) 与 [MIT 仓库](https://github.com/BocchiSlice/CTBakeGS) 提供浏览器内 DICOM/NIfTI→3DGS 转换和 PLY/SPZ 导出。论文给出 4–30 s、约 200 万 splats 和 800×800 约 68 FPS 等结果，但没有完整统一的体数据、质量阈值和硬件口径。

**编辑摘要：** 本批唯一“有真实代码、能马上打开”的项目，适合研究和教育原型；医疗数据应本地处理，输出不可用于诊断，作者性能数字必须在自己的数据与设备上重测。

### GraftRay：Gaussian 场景中的物理一致 mesh 插入

<!-- arxiv:2610.37036 -->
[GraftRay（arXiv:2610.37036）](https://arxiv.org/abs/2610.37036) 为 3DGS 场景估计 material/normal，以扩散先验与 extended emitters 驱动 hybrid path tracer，让插入 mesh 获得更一致的光照、阴影和反射。未核实到公开实现。

**编辑摘要：** 它瞄准“可看但不可进行物理合成”的 GS 痛点，方法价值高于单纯贴图；没有代码时无法判断路径追踪成本、材质估计误差或与 Web/XR viewer 的可集成性。

LingGS 与 SG²SLAM 见第 7 节。本期 8 个 arXiv ID 按 ID/标题去重：CTBakeGS 有实际代码，GeoGSplat/Honeycomb-Surfels 有项目页但无可运行 release，其余均为论文无代码；StereoSplat 明确按 revision 处理。

## 13. 今天最值得实际测试/部署的项目

### 1) PlayCanvas Engine 超大 splat fallback

- **为什么**：修的是明确的生产故障——超过设备 storage-buffer limit 后黑屏；回退后至少可见。
- **门槛**：WebGPU、包含 4M/5M/8M active splats 的测试资产；锁定 [d0127b10](https://github.com/playcanvas/engine/commit/d0127b10af116c63b4d3732488b2b8157eebeeb9)，不要只跟浮动 main。
- **测试**：覆盖 128/256 MiB binding limit、多 camera/layer、清空与重载；记录 fallback 触发、CPU sort time、首帧、交互 FPS、内存和是否恢复 GPU sorter。
- **预期收益**：把不可见故障变成可降级运行；风险是 CPU 排序在低端设备仍可能卡顿。

### 2) LichtFeld SAM2.1 mask-video

- **为什么**：operator removal 直接接入训练数据布局，减少外部脚本与格式转换。
- **门槛**：GPL-3.0 master、CUDA GPU、约 323 MB [SAM2.1 模型资产](https://github.com/MrNeRF/LichtFeld-Studio/releases/tag/model-sam2-video-v1)；先锁定 [103636f9](https://github.com/MrNeRF/LichtFeld-Studio/commit/103636f9ef1f342346dbe2ded117bc647b0b1ff1)。
- **测试**：静态/运动相机、鱼眼、遮挡、小人物、快速运动；抽查 `0=exclude/255=keep`、边缘 dilation 和连续失效恢复，再比较有/无 mask 的训练伪影。
- **预期收益**：更少摄影师鬼影、可复用数据集；风险是错误 mask 会永久删掉有效监督。

### 3) OOOSplat 0.7.1 pre-release

- **为什么**：三平台安装包已出现，generation policy、OOM retry、manual/bridge recovery 和导出链可以真正端到端验证。
- **门槛**：优先 Windows 11 x64；macOS 15+/Ubuntu 24.04 仍 alpha；需要 Brush 可用 GPU backend。
- **测试**：同一图像/视频跑 0.7.0 与 0.7.1，记录 registration、effective-pixel ceiling、最终 splat 数、峰值显存、一次 OOM retry、resume、PLY/SPZ/SOG round-trip 和最终质量。
- **预期收益**：失败更可解释、采样/重试更可控；风险是 pre-release 平台签名、兼容性和长任务恢复仍需验收。

Spirula match editor 是第四候选：如果已有明显 false matches 的 SfM 数据，修复收益可能高于重新训练。LichtFeld OpenXR 适合现场评审，但它目前只看不改，不应替代桌面编辑器。
