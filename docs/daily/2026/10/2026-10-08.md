## 2. SuperSplat / PlayCanvas 工具链

### Engine：streamed octree 改为 breadth-first LOD

[#9694](https://github.com/playcanvas/engine/pull/9694) 调整的是加载优先级而不是 splat codec：先 tier，再以“更粗 LOD 优先”，最后才比较节点距离。它保证整个视野得到 level N 后才开始 level N-1。粗层文件数通常少，额外等待应有限；真实收益会体现在首屏一致性、相机快速转向和带宽受限移动端，而不是峰值画质。**建议马上升级 master 做 A/B；发布版用户等正式 Engine release。** 要重点量化 first-meaningful-frame、全景最差区域质量、请求数、取消请求和相机跳转后的浪费带宽。

### SplatTransform：ZIP64 与统计正确性

[#352](https://github.com/playcanvas/splat-transform/pull/352) 给 SOG ZIP writer/reader 增加 ZIP64 EOCD、locator 和扩展字段；作者用约 4.3–4.5 GB 真包分别经 unzip、Python zipfile、bsdtar 验证，小包输出不变。实际影响是离线转换、归档和超大 chunk 集合不再被经典 ZIP 的 4 GiB/65,535 项限制卡住。**兼容性边界必须写进流水线：当前 Engine 不能读 ZIP64，大于 4 GiB 的 SOG 不能直接发布到 PlayCanvas runtime。**

[#351](https://github.com/playcanvas/splat-transform/pull/351) 修正 stats 对非线性显示变换的处理：scale 先 exp、opacity 先 sigmoid、f_dc 先转颜色，再用 Welford 在显示空间累计 mean/stddev，而不是对 raw 均值和标准差做一次变换。JSON shape 未改。它不会改变 PLY/SOG/SPZ 数据，却会改变质量审计与异常阈值，旧 stats 基线不可直接混比。

SuperSplat Editor、SuperSplat Viewer 本窗口没有新的 commit/release；未发现新的 selection/picking、histogram、camera/path、viewer export、shared viewer settings、WebGPU Editor 或发布 API 变化。公开博客、文档、论坛也没有新的技术公告。Discord 需要登录/加入的内容本轮未直接读取，也未采用转述。

### Semantic Lifting：代码、容器和复现路径已齐

[semantic-lifting-3dgs](https://github.com/ivanver02/semantic-lifting-3dgs) 是 [arXiv:2610.08756](https://arxiv.org/abs/2610.08756) 的实现，提供 Docker/Apptainer 流水线并复用 Inria 3DGS。默认镜像基于 CUDA 11.6，compute capability 默认 8.6，作者在 A100 上给出的单场景从零测试约 41 分钟；缓存 votes 后 beta sweep 约 4.5 分钟。许可沿用 Inria 非商用研究条款。属于“代码可跑的研究原型”，而非宽松许可生产组件。

## 5. Viewer / Editor / Web / Mobile / XR

[Spark Tour Studio](https://github.com/MisterE123/spark-tour-studio) 把本地 RAD/托管场景、可编辑 JSON、静态网站导出和离线 launcher 串成 Windows authoring 工作流。v1.11.0 对内容量变大的 tour 很实际：Places & Stories 可跨 scene/view/description/bubble 文本搜索，teleport 会考虑碰撞，加载时有 cover/progress，并在同一 renderer/WebXR session 内换场景。v1.11.1 的上下半球纯色通过线性颜色空间平滑过渡，并按眼睛用于 WebXR；旧单色配置保持兼容。**门槛：**Spark 2.3.1/Three.js，Windows authoring，Quest 仍需实机验收。

PlayCanvas 的 breadth-first LOD 与 LichtFeld 的 Spark page order 指向同一工程结论：移动/XR 体验首先受“最先到达哪些 page/chunk”控制，而不是仅由最终压缩率决定。建议把首屏最差块质量和头部转动后的恢复时间加入 viewer benchmark。

## 6. Compression / Format / LOD / Streaming

- **SOG/ZIP64：**工具端突破 4 GiB，但 runtime 断链；在 Engine 加 ZIP64 reader 前，应继续限制单 SOG 大小或拆包，不能因为转换成功就宣称发布成功。
- **RAD/Spark 分页：**LichtFeld [#3001](https://github.com/MrNeRF/LichtFeld-Studio/pull/3001) 的粗到细、全局后局部排列，解决的是预算内 page 可达性，不改变 codec。
- **LOD 请求策略：**Engine [#9694](https://github.com/playcanvas/engine/pull/9694) 解决网络调度顺序；它与资产排列协同后才构成稳定的 progressive streaming。
- **GSCV：**论文宣称用标准视频 codec 压缩 GS 序列，但 [公开仓库](https://github.com/Qi-Yangsjtu/GSCV) 仍只有 README“code coming”，没有许可证和实现，不能进入 codec 对比流水线。
- 本窗口未核到 SPZ、glTF Gaussian extension、OpenUSD、3D Tiles、MPEG GSC、Khronos 或 W3C/WebGPU 的新正式标准变更。

## 7. Training / Reconstruction / SLAM / Robotics / Mapping

Spirula 的 [8ea07447](https://github.com/harry7557558/spirula-studio/commit/8ea07447efc0460cda721cff799f2425513a54d3) 是今天重建主线：大 pair list/graph 超过 256 MB 时可以 memory-map 到输出目录旁；BA 遇到 GPU range/分配或 device-lost 可回退 host；implicit A_cp 路径减少 observation 级中间量。随附文档的 synthetic 300-camera/139 万 observation 测试中，dense 1119→675 MB、CG 553→331 MB，最终 cost 前七位一致；4194 图/787 万 observation 的作者实测从 93.6 秒/8392 MB 到 2.6 秒/3157 MB，6281 图/1248 万 observation 从 15.4 GB OOM 到 4356 MB。**证据 B，需注意求解器从 dense 到 CG 的口径，不可概括成统一“36×加速”。**

HEVC [#155](https://github.com/harry7557558/spirula-studio/pull/155) 则属于输入正确性：如果视频抽帧颜色已损坏，后续 SfM/训练再稳定也无意义。其未解决的两个 heif_test GPU encode/decode roundtrip 失败仍应保留为已知问题，专利相关路径默认关闭也未改变。

本窗口未发现可验证的新 Gaussian SLAM、机器人或地图集成 release；没有把论文-only 项目抬高为可部署方案。
