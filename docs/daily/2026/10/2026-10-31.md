## 2. SuperSplat / PlayCanvas 工具链

### Engine：`.lcc2` 从“编辑器可导入”升级为“运行时可流式直读”

[commit 81faeb72](https://github.com/playcanvas/engine/commit/81faeb7279f14423e809249a5285fc029bdfa358) 为 GSplat handler 注册 `.lcc2` parser。LCC2 的每个树节点持有该区域的一层 LOD，细化时父节点被子节点替换，底层 SOG splat 文件按需流入；新增 Tunis 示例从最粗层启动，待初始 frame ready 后切回设备 preset，示例预算为移动端 1M、桌面 4M。通用 viewer 示例同时增加 URL 打开、streamed scene budget 和 `.lcc2` 的 +Z-up 方向处理。

这不是把 LCC2 转成 PLY/SOG 的离线工具，而是让 Engine 直接消费 XGRIDS 的层级索引。对 Editor 没有新增选择/直方图操作，对 Viewer/SplatTransform 也没有新增导出格式；真正变化在发布端：大型 `.lcc2` 可以绕过全量下载/转码直接进入 WebGPU/WebGL 运行时。LCC2 仍是 XGRIDS 专有格式，开放 parser 不等于格式标准化。

### Engine：预算选择不再逐叶评估

[commit c7c7dc7b](https://github.com/playcanvas/engine/commit/c7c7dc7bbe668cea304fded76e61c0e22587d6f9) 在加载时把 SOG leaves-only `lod-meta` 重塑为层级：每个 node 持有一层并由 children 细化。运行时从根开始用 priority queue 选择收益最大的 refinement，第一处超出 splat budget 就停止，只访问 cut 附近节点；旧的 per-leaf tables、scale histogram 和内部 `lodDistanceShrink` 被移除。格式与现有 SOG 文件均不变。

实现还为“部分 children 已到、siblings 仍加载”保留引用，防止 cooldown 提前卸载；fallback finer nodes 的实际距离会进入 SH color update threshold；node AABB debug 显示当前 cut 与等待节点。预期收益主要是高节点数场景的 CPU 选择复杂度和加载稳定性，commit 没有给出跨设备帧时数字，不能写成固定倍数提升。

### SuperSplat / Viewer / SplatTransform 状态

[SuperSplat](https://github.com/playcanvas/supersplat) 窗口内只有 ESLint config 3.0 整理；Editor 仍为 3.7.0，没有新的 selection、histogram、camera path、publish API、SOG/SPZ/PLY/GLB/glTF 或 WebGPU 架构变化。[SplatTransform](https://github.com/playcanvas/splat-transform) 也只有 CI/release workflow 变化，仍为 3.10.3，无需升级。

[Viewer XR commit](https://github.com/playcanvas/supersplat-viewer/commit/725c3f2678f4162b2b888f5bce72697c326746f6) 则构成 1.42.0 的实质功能：AR placement 使用浏览器 plane/mesh hit-test，pinch、trigger 或触屏释放时放置，手机双指缩放/旋转；对象/场景按起始相机是否在 bounds 外判定，分别选择抓取或人在场景内移动。无 collision 的场景通过 256×256 splat picking 拟合近水平面作为站立地面；当前注释明确指出该 floor pick 只看到 sorted renderer，stochastic stereo frame 不留下可用 depth 时会保持上一次 floor。**建议立即测试，但不要在生产 XR 中关闭 fallback 地面/碰撞策略。**

## 3. 可实际运行的开源项目

### Spark Radix：新的 Three.js WebGPU renderer 分支

[官方仓库](https://github.com/sparkjsdev/radix) 的 `@sparkjsdev/radix` 0.0.1 可直接 `npm install three@0.186 @sparkjsdev/radix`，也可 CDN 导入；MIT，Node 开发环境 22.15+，TypeScript 5.7+。WebGPU 路径将 project、compact、radix sort 和 indirect draw 留在 GPU，无 readback；同一 scene 的多个 splat 对象合并排序后一次 draw，避免对象间透明混合错误。WebGL2 fallback 复用 TSL→GLSL，但排序在 worker，结果会比移动相机落后数帧。

`@sparkjsdev/radix/core` 无 Three/DOM 依赖，支持 PLY、compressed PLY、SPZ、RAD、RDX 读写；GPU 数据表每 splat 32 B，packed 16 B。renderer 支持 EWA、3DGUT、HTGS、rayGS 和 SH1–3。官方对五个 0.5M–10M 场景的自测称 Apple M3 Max/Chrome/1920×1080 下 WebGPU 平均为 SparkJS 2.3.1 的 1.37×，10M interior 为 9.2 vs 16.5 ms/帧；WebGL2 反而是 Spark 约快 1.09×。这是作者 benchmark，需在目标 GPU 和浏览器复测。

缺口决定其成熟度仍是“可实际测试/研究原型”：没有 LOD selection、paged streaming、内置 SOG、skinning、Spark 完整 raycast/SDF edit，也未覆盖最广设备。适合 renderer/RDX/PBR/多对象实验，尚不能替代 Spark 或 PlayCanvas 的生产级大场景发布链。

### Gaussian-Splat-Lite：主线切换 r187，生产先锁 SHA

[r187 commit](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/180e42e521dd7667aa0d14dca55552c96d98f307) 改动 WebGPU projection cache、accumulator、TSL material、capture、denoiser 与 WebGL fallback，follow-up [a5962983](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/commit/a596298356fbcd4e482d1629f70c93357d9ef6b3) 再把 fragment uniforms 打包并使用 raw texel coordinates。PLY/SPZ/SOG/RAD 能力没有被移除，但这是 breaking peer 版本迁移；当前 package version 仍显示 1.5.4，没有新的正式 tag。

建议分三组对照：WebGPU + r187、WebGL2 fallback + r187、现有 v1.5.4 + r186；记录首次 pipeline compile、稳定帧 GPU time、denoiser 前后画面、reversed depth、XR、cube mipmap、透明度与 render-target Y flip。没有作者 benchmark，不应仅凭“perf”标题宣称具体百分比。

## 6. Compression / Format / LOD / Streaming

本日格式/流式主线是“同一层级模型接入更多运行时”，不是新压缩标准：

- `.lcc2`：PlayCanvas Engine 新 parser 直接把 XGRIDS 树接成 streamed octree；节点的 splat 文件按需加载。它是专有格式的开源运行时实现，非 Khronos/W3C 标准。
- SOG `lod-meta`：文件不变，加载时从 leaves-only 元数据重建 hierarchy；预算算法和 pending-child 保活变化，不要求重新编码现有资产。
- Radix：core 可读写 PLY/compressed PLY/SPZ/RAD/RDX，但 0.0.1 没有内置 SOG 和 LOD/paging；RDX 为其自身 chunked 格式。
- Gaussian-Splat-Lite：PLY/SPZ/SOG/RAD 的主线 renderer 迁移 r187，没有新格式版本或压缩率声明。

窗口内未核实到 KHR_gaussian_splatting、OpenUSD Particle Fields、3D Tiles、MPEG GSC、SPZ 或 SOG 的新批准版本。任何“10×”“8–26×”等旧格式宣传均未作为今日性能结论重复收录。

## 7. Training / Reconstruction / SLAM / Robotics / Mapping

### Spirula：先避免错误硬件路径

[c8594b65](https://github.com/harry7557558/spirula-studio/commit/c8594b657158d33c2635146aaaf5b8341ded5dfd) 对 AMD GPU 检查 cooperative matrix 与 float32 atomic add 支持；维护者将 pre-RDNA3 的驱动路径标记为软件仿真、存在 NaN 与约 250× slowdown，默认禁用，`NN_COOPMAT=1` 可显式覆盖。这个 250× 没有给出具体 GPU、场景和质量口径，只能当作触发保护的作者诊断，不能外推为升级后整体训练加速。建议 RX 6000/5000、RDNA3 和 NVIDIA 各跑相同 seed/场景，记录 NaN、step time、VRAM 和质量。

同日 master 还把版本推进到 2026.10.30、重做 PSNR 图、修正 SfM 内存帮助文本，并在 360-camera feature mask 默认提示加入 water/wave；这些是可用性补充，不单列重大更新。

### visloc-rs：融合先验有收益，也有反例

[PR #429 merge](https://github.com/rsasaki0109/visloc-rs/commit/0577f7aff03a99bf50bfb9f15c16569d6cb79c9f) 给出四个 ETH3D 场景的端到端数据。ground-truth poses、1600×1067、8 GB laptop GPU 的 CUDA MVS 在 pipes/terrace/kicker/courtyard 分别用 53/105/138/182 s，2 cm cloud F1 为 79.2/88.5/83.6/84.3%。prior-30 splat 训练 30k steps、每场 6.5–17.5 分钟；前三场与 MVS depth 融合的 mesh F1 均值 81.2%，六场均值 75.8%。

关键反例是 pipes：plain splat 自身 mesh 仅 16.7%，拿它补 MVS depth 后 67.8%，低于 MVS-only 68.9%；prior-30 才到 76.8%。courtyard 1 cm mesh 为 1.0–1.8 GB，在 11 GB WSL2 VM 评测 OOM。结论应是“几何先验让 GS 成为更可靠的 MVS completion source”，而不是“GS 无条件提升 mesh”。

## 13. 今天最值得实际测试 / 部署

### 1) PlayCanvas LCC2 + hierarchy-cut LOD

- **为什么**：格式 parser、层级选择和通用 URL viewer 同时落地，改变超大 XGRIDS/SOG 场景的发布路径。
- **门槛**：从 Engine main 锁定 `81faeb72` 与 `c7c7dc7b`；准备 `.lcc2`、既有 SOG `lod-meta`、移动/桌面 WebGPU 与 WebGL2 设备、可控延迟/丢包代理。
- **测试**：1M/4M/10M/40M budget；根→children refinement；siblings 延迟/失败；camera 快速穿越；tab suspend/resume；renderer 切换；SH update；显存、网络峰值、LOD selection CPU p95/p99；与旧逐叶路径画面 cut 对比。
- **预期收益**：无需离线转 PLY/SOG 即可直接运行 LCC2，并降低高节点数场景的 LOD 选择工作；具体倍数需本地测。当前成熟度：main 可实际测试，未进入已确认稳定版。

### 2) Spark Radix 0.0.1 renderer A/B

- **为什么**：Three.js 生态新增真正的 WebGPU projection/sort/draw 全 GPU 路径，且多对象共享排序与一次 draw。
- **门槛**：`npm install three@0.186 @sparkjsdev/radix`；WebGPU 浏览器与 WebGL2 fallback；0.5M、2M、10M 场景，至少包含两个互相穿插的 splat 对象。
- **测试**：官方五场景口径、首次编译、稳定 GPU/CPU frame time、透明混合、相机快速运动、XR stereo、PLY/SPZ/RAD/RDX round-trip、16/32 B layouts；再与 SparkJS/PlayCanvas/GSL 同机对照。
- **预期收益**：WebGPU 端降低 CPU 往返和多对象 draw/sort 成本；没有 LOD/paging 时大场景内存与网络仍是硬限制。当前成熟度：实验性 0.0.1，不直接替换生产 renderer。

### 3) SuperSplat Viewer 1.42.0 XR 交互

- **为什么**：AR placement、grab、软阴影、无 collision floor 与 hand/controller/screen 输入形成完整交互闭环。
- **门槛**：HTTPS/WebXR；Quest/Android AR/Vision Pro 至少两类设备；带/不带 collision 的对象和室内场景；sorted 与 stochastic renderer。
- **测试**：平面/mesh hit-test、水平面阈值、双指 scale/turn、对象/场景误分类、floor pick 丢失、menu/ice-cream 状态互斥、session 重进和性能模式。
- **预期收益**：分享 viewer 可直接承担 XR 展示和轻交互，不再依赖定制宿主完成基本放置/抓取。当前成熟度：正式 1.42.0，但新 XR 路径仍应做设备矩阵回归。
