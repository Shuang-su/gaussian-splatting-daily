## 2. SuperSplat / PlayCanvas 工具链

### Engine：WebGPU XR 避免每眼重复方向光阴影

[Engine #9698](https://github.com/playcanvas/engine/pull/9698) 改的是 render-pass 调度：方向光 shadow map 与视点无关，WebGPU XR 不应为左右眼各画一次。合入后 shadow pass 对 stereo views 共用一次；这直接释放 XR GPU 帧时间，对“splat 主体 + mesh 遮挡/地面/人物 + 实时方向光”的混合场景最有意义。它不改变 Gaussian sorting、projection、SOG/SPZ/PLY 解码、selection/picking 或纯 splat 渲染质量。**建议测试：**同一 Quest/头显、同一场景分别记录 GPU shadow pass、总帧时、眼分辨率和阴影级联数，避免把 CPU 或 splat sorting 改善误算给该 PR。

Engine 同时推进 2.24.0-beta.5，但这是 beta 上下文，不应替代稳定版升级判断；最近稳定版仍是 2.23.1。SuperSplat Editor、SuperSplat Viewer 和 SplatTransform 在本窗口没有新 commit、merged PR 或 release，因此没有新的 SOG/SPZ/PLY、viewer export、shared viewer settings、camera animation、selection/histogram、WebGPU Editor、LOD/streaming 或 stochastic rendering 变化可报。官方博客/文档/论坛也未发现同窗口的新技术公告。Discord 需登录或加入服务器的内容本轮未直接读取，也未采用转述。

## 4. 4D / Dynamic Gaussian

今天 4D 主线来自论文而非可运行代码：

- **[DynStream: Streaming Dynamic Gaussian Reconstruction from Long Monocular Videos](https://arxiv.org/abs/2610.09720)**：在线处理长、无位姿视频，用局部窗口构建动态 Gaussian，再对齐/融合为全局一致场景，目标是避免逐场景优化。**论文无代码；研究原型；A。**
- **[S2Tok: Streaming 3D Gaussian Reconstruction with Persistent Spatial Tokens](https://arxiv.org/abs/2610.08978)**：持久自适应 spatial tokens 保存场景状态，每步只消费当前帧、不保留 KV cache，每 token 解码 32 个 Gaussians。[项目页](https://s2tok.github.io/) 明示代码待发布。**论文+项目页、无实现；A。**
- hustvl/4DGaussians、fudan-zvg/4d-gaussian-splatting、Dynamic3DGaussians 上游无本窗口关键变化。

对工程团队而言，今天更值得做的是为未来 streaming 模型准备统一的“增量状态大小、每帧时延、漂移、回环后全局一致性、长序列显存”基准，而不是尝试部署尚未公开的模型。

## 5. Viewer / Editor / Web / Mobile / XR

PlayCanvas [#9698](https://github.com/playcanvas/engine/pull/9698) 是今天唯一明确的 Web/XR runtime 变化：WebGPU XR 中方向光阴影 pass 不再左右眼重复。它对纯 SOG viewer 影响有限，对叠加实景 mesh、角色或遮挡代理的 viewer 更有价值。需要注意，PR 不涉及 WebGL，Quest 浏览器最终收益取决于实际走 WebGPU、阴影级联和场景中 mesh draw 占比。

LichtFeld [#3049](https://github.com/MrNeRF/LichtFeld-Studio/pull/3049) 则把大于 2M splats 的 gallery 发布默认切成 SSOG，使手机端更容易先拿到粗层而不是一次性加载全场。它与昨天 PlayCanvas breadth-first LOD 的方向一致：资产层次与请求调度需要配套。今天没有新的 SuperSplat editor、selection/picking、camera/path、shared viewer settings 或 WebXR viewer export 变化。

## 6. Compression / Format / LOD / Streaming

- **SSOG 自动化：**LichtFeld #3049 的 2M 阈值、≤500k 最粗层、最多 8 层和 256k units 是今天唯一直接改变发布默认值的格式链变化。它提高“默认可用性”，但不是新 codec，也未给出跨场景压缩率/质量曲线。
- **RAD flatten 正确性：**#3092 修复的是解码后/加载后物化数据，而非 RAD bitstream。其重要性在于错误会跨格式扩散：源 RAD 看似正常，导出 PLY/SPZ/SOG/GLB 等却被污染。
- **超大图分带：**#3108 的 bands 是 viewport image export 的 GPU 内存策略，不是 Gaussian LOD；不要将 8K–966MP 的显存结果外推到实时 viewer。
- 本窗口未核到 SPZ、SOG 规范、glTF Gaussian 扩展、OpenUSD、3D Tiles、MPEG GSC、Khronos 或 W3C WebGPU 的新正式标准落地。

## 7. Training / Reconstruction / SLAM / Robotics / Mapping

Spirula 今天同时推进重建前端、训练内核与 mapping 坐标稳定性，优先级最高。实际测试顺序建议是：先用一套 pinhole 小场景确认 RoMa cache/manifest 与原 SfM 不回退，再用 fisheye/equirectangular 检查 original-image 路径，最后用 60MP HDR 和远离原点的地理场景复核显存与 `scene_transform.json` 的 eval/mesh 一致性。

**[ActiveLang: Active Open-Vocabulary 3D Mapping with Dual-Gaussian Representations](https://arxiv.org/abs/2610.09518)** 把 geometry/appearance/semantics 放入双 Gaussian 表示，并用不确定性引导主动探索，在 Replica 与 ScanNet++ 上评估。**论文无代码；研究原型；A。**

**[LighTROcc: Instance-Centric Gaussian Mixtures for Present and Future Occupancy](https://arxiv.org/abs/2610.09444)** 面向环视相机自动驾驶 occupancy，用 instance-centric 3D Gaussian mixture 表示当前与未来占用，在 nuScenes 上验证。**论文无代码；研究原型；A。**

固定 SLAM/robotics 仓库和厂商页面未发现同窗口可下载的新 SDK、权重或生产 release。

## 8. Avatar / Human / Generative 3D

**[Counterfactual Route Optimization for Gaussian Head Avatar Modeling](https://arxiv.org/abs/2610.09791)** 用短视野 lookahead 在 geometry、appearance 与 joint optimization route 之间做状态依赖选择。**论文无代码；A。**

**[Efficient 3D Gaussian Head Avatars for Edge Devices](https://arxiv.org/abs/2610.09821)** 声称相对其基线减少 94% FLOPs、70% 参数和 81% 模型体积，并展示 CPU 与 browser ONNX Runtime 方向；但论文摘要明确代码、模型和评估尚待发布。**论文无代码/权重；性能待复核；A。**

**[DeltaSplat: Iterative Residual Refinement for Feed-Forward Gaussian Splatting](https://arxiv.org/abs/2610.09853)** 用 Plücker rays 与 depth cues 做逐 Gaussian residual refinement，作者报告只增加 2.2% 参数，在 DL3DV 达 26.64 dB、比所用 backbone 高 1.75 dB。**论文无代码；A。**

这些条目今天都不能直接运行；不要因“browser/edge”措辞误判为已有 Web 部署包。

## 13. 今天最值得实际测试 / 部署

### 1) LichtFeld RAD flatten + 多格式回归（最高优先）

**固定版本：**合入 [#3092](https://github.com/MrNeRF/LichtFeld-Studio/pull/3092) 后的 master。  
**门槛：**GPL-3.0、源码构建、Vulkan/CUDA 环境；准备一个已加载 RAD 项目。  
**测试：**记录 flatten 前后 splat 数、opacity/SH 统计，再分别导出 PLY、SPZ、SOG/SSOG、GLB 和 gallery，渲染同一相机并比较 PSNR/SSIM。  
**预期收益：**防止看似成功的跨格式发布静默改变数量和不透明度；这是今天最直接的数据正确性风险。

### 2) Spirula 60MP/120MP 显存与暂停恢复

**固定版本：**至少 [56c3c41d](https://github.com/harry7557558/spirula-studio/commit/56c3c41db108a8f7a3cb5cb0a991fddb238b2f50)，如要 RoMa/渐进训练则固定 [e71e0799](https://github.com/harry7557558/spirula-studio/commit/e71e079961de2949c9a3d6280f896df5451b0301)。  
**门槛：**GPL-3.0；目前 Windows/Vulkan 证据最完整；12GB GPU 可优先复现。CUDA/Linux/macOS 需自行构建验证。受限模型下载需处理 `--accept-license`。  
**测试：**同一 HDR 数据分别跑 master 前后，记录 pool+scratch 峰值、step time、最终质量；在阶段切换和停止点分别保存/恢复。  
**预期收益：**若作者数据可复现，可把超高分辨率训练硬件门槛显著下移，并降低 UI 切页导致 OOM 的概率。

### 3) LichtFeld 超大截图 + mesh 遮挡

**固定版本：**[#3108](https://github.com/MrNeRF/LichtFeld-Studio/pull/3108)、[#3109](https://github.com/MrNeRF/LichtFeld-Studio/pull/3109)、[#3111](https://github.com/MrNeRF/LichtFeld-Studio/pull/3111) 全部合入后的 master。  
**门槛：**5M 级场景、可见 mesh、足够主机内存和磁盘；GPU 显存不再应随整张输出线性增长。  
**测试：**8K/16K/32K 与透明背景，检查 band seam、mesh/splat depth、解码像素、PNG 时间和峰值 VRAM。  
**预期收益：**把巨幅离线输出从高端 GPU 特例变成可计划的标准工作流；对地图、建筑和印刷交付尤其直接。
