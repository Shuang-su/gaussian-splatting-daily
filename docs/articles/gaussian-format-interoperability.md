团队把一个扫描结果交给另一个工具，常常先问“支持什么格式”。这个问题必要，但不充分。两个软件可以都接受同一个后缀，却对坐标、颜色、球谐属性或编辑状态作出不同处理。

OOOSplat 的一项主分支更新把标准与压缩 PLY、SOG、SPZ、SPLAT、KSPLAT 接入项目导入流程，并保存来源线索。它减少了手动转换与建项目的步骤，但截至相关日报观察点仍未独立发版，不能把支持清单当作全部组合已经通过验证。[原始提交](https://github.com/ooolabdev/ooosplat/commit/9cd6b5ab1364)

## 先固定文件身份，再比较画面

开始转换前，保留原文件、生成工具版本和哈希。另存转换结果并记录完整参数，避免后来无法区分“原始资产变了”和“转换器行为变了”。

第一次检查可以从文件数量、字节、解码成功与高斯数量开始，但画面相似也不意味着属性全部保存。例如，较低层级的颜色可能在固定视角中看起来接近，而转动相机后才暴露视角相关外观的差异。

## 将属性与显示结果对应起来

下表是验证顺序，不表示所有格式都保存这些字段。对不支持的属性，应明确记录丢失、重算或外部保存的方式。

| 检查项 | 数据侧核对 | 画面侧核对 |
|---|---|---|
| 位置与单位 | 包围盒、轴向、尺度与原点 | 是否旋转、镜像或偏移 |
| 形状 | 缩放、旋转及其编码约定 | 薄结构、轮廓与高斯伸展方向 |
| 透明度 | 数值范围及变换方式 | 雾状区域、边缘和重叠表面 |
| 颜色与球谐 | 系数数量、排列和量化 | 固定视角与连续转动视角 |
| 场景附属信息 | 相机、许可、来源与编辑状态 | 是否仍能继续原有工作流 |

如果目标工具无法表达某个字段，合理的交付方式是把限制写清，并保留原资产。不要用一个看起来正常的预览截图替代属性记录。

## 文件更小，不一定加载更顺畅

压缩减少传输字节，但还要付出解码与资源准备成本。流式场景另外需要分块、层级索引和能按需读取它们的运行时；这些条件不能从文件后缀单独推断。

例如 Gaussian-Splat-Lite 的流式 SOG 文档要求层次索引入口，并明确区分普通 SOG 文件。这说明在比较“支持 SOG”时，需要继续问清支持的是哪一种资产组织形式。[固定版本文档](https://github.com/WilliamLiu-1997/Gaussian-Splat-Lite/blob/v1.3.1/docs/SogStreamScheduler.md)

:::details[一组可重复的往返验证]

1. 选择包含薄结构、透明边缘和明显视角相关颜色的资产，保留原文件与固定相机路线。
2. 在原工具中记录属性、包围盒、图像与资源占用，再用明确参数转换。
3. 在目标工具复用相机与显示设置，核对对应属性和画面。
4. 在目标工具支持的前提下转回，检查哪些字段保持、量化、重算或丢失。
5. 把发现写入该版本组合的兼容记录，保留失败样本，避免将一次成功推广到全部资产。

:::

## 交付结论应写到具体组合

有用的兼容记录应包括来源版本、目标版本、格式版本、转换参数、资产类型和已知限制。“这组工具与资产通过指定检查”能指导下一次交付；笼统的“格式通用”则很难帮助排查异常。

对于需要地图定位、进一步编辑或二次训练的项目，还应把附属数据一并保存。查看器只显示出模型，不能证明下一位接手者已经拿到完整的工作材料。
